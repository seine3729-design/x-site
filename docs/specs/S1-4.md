# S1-4 前台内容读接口

任务：`11` S1-4。依赖 S1-1（内容表，迁移 00004）、S0-4（读穿缓存）、S1-3（后台内容 CRUD）、S1-5（分集可播放状态）均已完成。
目标：Web（经 BFF）与 APP 能读到剧详情、频道、标签、探索、专题，统一的可见性规则与缓存头；自动专题的选剧规则在这里执行。

## 范围

| 接口（`/api/v1` 下） | 说明 | 分页 | 缓存 |
| --- | --- | --- | --- |
| `GET /dramas/:id` | 剧详情 + 分集 + 相关推荐 | — | 120s |
| `GET /channels/:slug` | 频道（维度取值落地页） | 页码（≤ 100 页） | 60s |
| `GET /tags/:slug` | 标签聚合 | 游标 | 60s |
| `GET /explore` | 探索：分面 + 筛选 + 排序 | 游标 | 30s |
| `GET /topics` | 专题列表 | 游标 | 300s |
| `GET /topics/:slug` | 专题详情（剧 + FAQ） | — | 300s |

范围外：首页区块编排 `/api/v1/home`（S3-1）、搜索与联想（S3-4）、榜单（S3-5）、资讯（S3-7）、刷剧流 `/feed/shua`（随 W1-6 / M1-4 的接口在 S3-1 一并提供）、选源与播放地址（S1-7 / S1-8，本任务只给 `playable` 标记）、个人化数据（追剧 / 历史 / 点赞，S2-3）、演员（模块已在 S1-3a 删除，表与接口都已移除，`03` 第 3.2 节的「演员」行随该任务清理）。

## 可见性规则（`03` 第 3.1、3.2 节）

| 对象 | 前台可见条件 | 不可见时 |
| --- | --- | --- |
| 剧 | `deleted_at IS NULL AND status='published' AND (publish_at IS NULL OR publish_at <= now())` | 404 `NOT_FOUND` |
| 分集 | 全部返回；`playable = (media_status='ready')` | 未转封装的分集标 `playable=false`（前台显示「敬请期待」） |
| 标签 | `status='active'`；`merged_into_id` 不为空时跟随到目标标签（`canonical_slug` 给客户端做规范链接） | 404 |
| 敏感标签（`is_hidden`） | 可按 slug 直接访问，响应标 `is_sensitive=true`（前台过年龄门并输出 `noindex`）；**不出现在探索分面里** | — |
| 频道 | `is_channel AND status='active'` | 404 |
| 分面里的维度 / 取值 | 维度 `status='active' AND show_in_explore`，取值 `status='active'` | 不返回 |
| 专题 | `status='published'`；列表另加 `list_in_index`（未收录的专题仍可按 slug 直接打开） | 404 |

404 一律用 `NOT_FOUND`「内容不存在或已下架」，不区分「不存在」与「已下架」，避免泄露存在性。

响应里不出现后台字段：`status`、`publish_at` 之外的时间戳、`view_base`、`hot_score`、`source`、`deleted_at`、`media_status`、`video_object_id`、`key_ver`、`renditions`。播放次数以 `play_count`（= `view_base + view_count`）输出。

## 规则

- **排序**：`latest`（上架时间，缺省时按创建时间）/ `hot`（`hot_score`）/ `recommend`（`sort_weight`）/ `random`，默认 `latest`；白名单外的值 400。
- **游标分页**：`{ list, next_cursor, total }`，`cursor` 不透明，`limit` 1–60（默认 24）。编码为 `base64url("<sort>|<seed>|<value>|<id>")`，SQL 用 `(排序列, id) < (值, 编号)` 行值比较（迁移 00004 已为此建复合索引）。排序与游标里的排序不一致、或游标解不开时 400「分页参数无效」，避免把游标当偏移量误读。
- **随机排序**：不用 `ORDER BY random()`（每页结果会重复或漏项）。按 `md5(id || '|' || seed)` 排序，`seed` = 10 分钟窗口的时间戳并写进游标，所以同一轮翻页顺序稳定、下一个窗口换一批。`03` 第 3.2 节写的「预生成随机序列表」在片库规模需要时再做（当前 1 万剧实测见「验收」）。
- **上新窗口**：`all`（默认）/ `7d` / `14d` / `30d` / `90d`，按 `coalesce(publish_at, created_at) >= now() - 窗口` 过滤。
- **探索筛选**：`terms=<维度slug>:<取值slug>`（逗号分隔，≤ 8 项，**全部满足**，与自动专题规则一致；取值 slug 只在维度内唯一，所以必须带维度）、`tag=<标签slug>`、`finished=true|false`、`window=`、`sort=`。筛选项写死在查询串里，服务端按校验后的参数生成缓存键（不用原始查询串，避免参数顺序或大小写造成缓存击穿）。
- **分面**：只在第一页（没有 `cursor`）返回，无限滚动的后续页不重复下发。分面不含每项的命中数（代价高），页面上的「查看 N 部」用结果的 `total`。
- **频道**：页码分页（`07` 第 0.1 节：只有前台频道页用页码），`page` ≤ 100、`page_size` ≤ 60（默认 24）；超过最大页数返回空列表而不是报错。
- **自动专题**：`rule_json = { term_codes, tag_id, sort, window, limit }`，同时满足全部取值编号与标签，按 `sort` 排序取前 `limit`（1–60，默认最新 / 不限 / 24）。规则引用的取值编号或标签已被删除时按「少一个条件」处理还是返回空？**按原样执行**：`code` 查不到就没有剧满足它，结果为空列表，不报错。
- **手选专题**：按 `topic_drama.sort` 顺序，过滤掉不可见的剧；一次最多返回 200 部（编辑型内容，不分页）。
- **相关推荐**：同标签或同维度取值召回，按「共同项数 → 热度 → 编号」排序取 12 部，排除自己与不可见的剧。
- **缓存**：读穿缓存（`store/cache`，singleflight + TTL 抖动）；TTL 见上表。每个响应带 `ETag`（载荷的 SHA-256 前 16 字节，随缓存一起存，命中缓存时不重算）与 `Cache-Control: public, max-age=0, s-maxage=<TTL>, stale-while-revalidate=300`。加密请求的响应被中间件强制改为 `no-store`（每个响应密钥不同），`s-maxage` 只对 BFF 明文直连生效；`ETag` / `If-None-Match` 两种情况都有效。
- **精确失效**：改剧 / 分集会让 `content:drama:<id>` 过期前仍返回旧值（TTL 120s）。本任务不做后台写接口的主动失效（S4-4 缓存管理统一提供），列表类 TTL 都 ≤ 60s。

## 接口与数据

契约写在 `service/api/openapi.yaml`（0.12.0），`07` 第 1 节「站点与内容读取」同步。

新增迁移 00013：只加一个部分索引 `drama_public_latest_idx`。`hot`、`recommend` 直接用迁移 00004 的 `drama_status_hot_idx`、`drama_status_recommend_idx`；`latest` 的排序键是 `coalesce(publish_at, created_at)`（已上架的剧一定有上架时间，极少数历史数据没有时按创建时间排，这样游标的行值比较里不会出现 NULL），与 00004 的 `drama_status_publish_idx` 不是同一个表达式，所以单独建。筛选用 `drama_tag_tag_idx`、`drama_term_term_idx`。三种排序都有 1 万部剧上的 `EXPLAIN` 断言（不扫全表、不排序）。

代码落点：`db/queries/content_public.sql`（前台查询）、`store/pg/content_public.go`（`content.PublicRepo` 实现）、`domain/content/public*.go`（参数校验、游标、规则执行、缓存）、`http/public/content/`（handler + 路由）。前台与后台共用 `domain/content` 的类型，但仓储接口分开（`Repo` / `PublicRepo`）。

## 验收

- 可见性规则（草稿 / 下架 / 定时未到 / 回收站 / 停用取值 / 隐藏标签 / 未发布专题）有 PostgreSQL 集成测试。
- 游标分页翻完全部数据不重不漏（含 `random`）、分面、自动专题规则、相关推荐有集成测试；排序走索引有 `EXPLAIN` 断言。
- 游标编解码、参数校验、缓存键规范化有单元测试；handler 有状态码 / 业务码 / 缓存头 / 304 测试。
- 1 万部剧的本地数据集上六个接口 P99 ≤ 150ms（空缓存，含 `random` 排序）。
- 临时脚本用真实请求按 `openapi.yaml` 校验全部接口的请求与响应。

## 假设（需确认）

1. 探索的多个取值是「全部满足」（与自动专题规则一致），不是同维度内「或」。单选维度本来只能选一个，多选维度选两个取值即「同时具备」。
2. 探索的 Tab：`04` 第 3 节原为「剧集 / 演员 / 专题」，演员模块已删除，所以剧集 Tab 用 `/api/v1/explore`、专题 Tab 用 `/api/v1/topics`，不做 `tab=` 参数。
3. 剧详情按数字 ID 取（`/d/:id`），剧的 `slug` 可为空，不做按 slug 访问。
4. 随机排序用 10 分钟稳定种子 + 哈希排序，不建随机序列表（见「规则」）。
5. 专题列表不返回每个专题的剧数与封面拼图（需要按专题再查一次），只给标题、简介、slug。
