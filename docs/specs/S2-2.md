# S2-2 防撞库与注册约束

任务：`11` S2-2。依赖 S2-1（注册 / 登录）。
目标：登录失败计数 + 人机验证挑战 + 统一错误提示与相近耗时；注册须带 `ack_no_recovery`。验收：用户名不存在与密码错误响应一致（S2-1 已做）；连续失败 5 次要求挑战。

在 S2-1 的注册 / 登录之上加「失败过多要求人机验证」的防撞库层。与后台登录（`docs/03` 第 2.3 节）的「锁定 429」不同，用户端用更友好的**挑战**：失败到阈值后要求通过一次工作量证明（PoW），通过了仍可继续尝试、不锁定账号（真人几秒解一次，自动化撞库则被显著拖慢）。

## 机制

### 失败计数（Valkey）
`user.Service.Login` 用 `FailureCounter`（`cache.Counter`，Get/Incr/Reset）按两个维度计数：用户名 `u:<username>`、IP 前缀 `ip:<prefix>`，滑动窗口 15 分钟（最后一次失败后到期清零）。密码错误 / 用户名不存在都 `Incr` 两个维度（不存在也计数，防枚举）；登录成功 `Reset` 用户名维度（IP 维度自然过期）。

### 人机验证挑战（自建 PoW）
- **签发** `GET /api/v1/auth/challenge`（`Guard.Issue`）：生成 128 bit 随机 nonce，存 Valkey `challenge:<nonce>` = 难度、TTL 2 分钟，返回 `{nonce, difficulty, expires_in, algorithm}`。`algorithm = sha256-leading-zero-bits`。
- **求解**（客户端）：找 solution 使 `SHA-256(nonce + ":" + solution)` 的二进制前 `difficulty` 个 bit 为 0。难度固定 18 bit（约 2^18 次哈希，浏览器 / APP 通常 1 秒内；校验只需一次哈希）。
- **校验** `Guard.Verify`：`ChallengeStore.Take`（Valkey `GETDEL`）原子取出并删除 nonce —— 保证一次性、防重放；不存在（已用 / 过期）即失败；再 `pow.Verify(nonce, solution, difficulty)`。

### 登录门禁
`Login` 开头：若用户名计数 ≥ `userFailThreshold`(5) 或 IP 计数 ≥ `ipFailThreshold`(20)，则要求挑战——请求体没带有效 `challenge` 时返回 428 `CHALLENGE_REQUIRED`；带了且 `Guard.Verify` 通过才继续校验密码。计数器故障时放行（不因 Valkey 抖动把所有人挡在挑战后）。通过挑战且密码正确即登录成功、清用户名计数；密码仍错则继续计数（下次仍要挑战）。

契约见 `service/api/openapi.yaml`（S2-2 记为 0.38.0）：新增 `GET /api/v1/auth/challenge`（返回 `AuthChallenge`）；`LoginRequest` 新增可选 `challenge`（`ChallengeAnswer{nonce, solution}`）；登录失败过多返回 428 `CHALLENGE_REQUIRED`。`docs/07` 的 challenge / login 行、`docs/03` 第 2.2 节防撞库已同步。无数据库迁移。

## 配置

无新增配置。失败计数与挑战 nonce 都存 Valkey（键前缀 `xsite:auth:login_fail:`、`xsite:auth:challenge:`）。

## 验收

- `11` 的「用户名不存在与密码错误响应一致」：S2-1 已做（`Equalize` 等代价 + 统一 `NEED_LOGIN`），S2-2 保持。
- `11` 的「连续失败 5 次要求挑战」：本机真实容器端到端——同一用户名连续 5 次错密码（均 401 `NEED_LOGIN`）后，第 6 次（即便密码正确、无挑战）返回 428 `CHALLENGE_REQUIRED`；`GET /api/v1/auth/challenge` 取挑战、本地解 PoW、带 `challenge` 登录成功（200 role=user）；登录成功后计数清零、再登录无需挑战；用过的 nonce 重放返回 428（一次性）。
- 单测：`internal/pow`（求解后校验通过、解绑定 challenge、空解 / 难度边界 / 错误解拒绝、前导零计数）；`user.Guard`（Issue→Verify 通过、一次性、空 / 未知 nonce / 错误解拒绝）；`user.Login`（失败达阈值要求挑战、无效挑战仍要求、有效挑战放行并清计数、失败累计到阈值后即便密码对也先要挑战、用户名与 IP 两维度计数）；`http/public/auth`（challenge 接口字段、login 挑战透传、428 映射）。
- 集成：`cache.ChallengeStore`（Valkey 存入、GETDEL 一次性取出、过期）。
- 回归：`go build ./...`、`go vet ./...` 通过；相关包 `go test` 全绿。

## 假设（需确认）

1. **挑战触发阈值**：用户名 5 次、IP 前缀 20 次（`docs/03` 第 2.2 节字面是「同用户名或同 IP 连续失败 5 次」；IP 维度放宽到 20 以免 NAT 下多个真人共用出口 IP 被频繁要求挑战，挑战虽温和但慢设备解 PoW 仍有成本）。如需严格按 5，调 `ipFailThreshold`。
2. **PoW 难度 18 bit**：兼顾「挡自动化」与「真人 / 慢设备不被卡太久」；可按线上观测调整（难度随挑战下发，客户端不写死）。
3. **只做自建 PoW**，不接第三方验证码；接口形状（challenge/answer）可容纳未来替换为第三方。
4. **失败计数维度与窗口**：用户名 + IP 前缀、滑动 15 分钟（与后台登录一致）。
