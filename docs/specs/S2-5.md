## 机制（评论）

- **作者身份**：HTTP 层从 `middleware.CurrentAccess` 取身份——注册用户 → `Author{UserID}`，游客 → `Author{GuestID}`（`Subject` 是 `guest_device.id`），匿名（无令牌）→ 401。点赞仅注册用户。
- **发表校验顺序**（`CommentService.Create`）：评论总开关（`features.comments`）→ 游客额外过 `features.guest_interaction`（关则 401 引导登录）、注册用户过禁言（`user.status=muted` → 403）→ 清洗（去控制字符、保留换行、trim）+ 长度 1–500 → 同作者相同内容 10 秒去重（Valkey SET NX，键含作者 + 内容 SHA-256，重复 409）→ 屏蔽词 `Evaluate`（block → 400；mask → 存替换文本；review → `status=pending`）→ 先审后显（`comment_policy.pre_moderation` 或命中 review 置 pending）。
- **列表**：游标分页，latest 用 `id` 游标（`id < cursor`，倒序）、hot 用 `(like_count, id)` 复合游标；只含 `status=visible`、未删；`LEFT JOIN "user"` 取昵称 / 头像，游客展示「游客」、不暴露用户名。
- **删除**：软删（`deleted_at`），作者不匹配返回 404（不暴露他人评论存在）。
- **点赞**：`comment_like` 幂等插入（`ON CONFLICT DO NOTHING`）+ 事务内累加 `like_count`，仅注册用户（游客点赞存本机、不计公开数）。
- 富文本一律按纯文本处理（前台渲染时转义），表情以 `[码]` 留在文本里；带图评论（`image_ids`）依赖图片管线 S6-13，本任务不收图、`image_count` 恒 0。

## 机制（弹幕）

- **发送校验顺序**（`DanmakuService.Send`）：弹幕总开关（`features.danmaku`）→ 游客额外过 `features.guest_interaction`、注册用户过禁言（复用 `authorCanPost`）→ `time_ms ≥ 0` → 清洗（换行折成空格、trim）+ 长度 1–40 → 颜色白名单（去前导 `#`、转大写归一；缺省白 `FFFFFF`；非白名单 400）→ 屏蔽词 `Evaluate`（block → 400；mask → 存替换文本；review → `status=pending`）。
- **颜色白名单**：10 个常用色（白 / 黑 / 红 / 橙 / 黄 / 绿 / 青 / 蓝 / 品红 / 紫，`RRGGBB`），在领域层维护。
- **拉取**：`[from_ms, to_ms)` 窗口，服务端把窗口夹到 ≤60 秒、单窗口 ≤300 条、仅 `status=visible`、按 `time_ms` 升序；`DanmakuView` 只给播放器需要的 `id/time_ms/content/color`。公开读，`Cache-Control: public, max-age=30`（CDN 可缓存，键含窗口参数）。
- **与评论的差异**：弹幕**不做**重复内容去重（docs 未要求）；先审后显目前仅由命中 review 词触发（全局「弹幕先审后显」开关随后台审核页 §24，与 `comment_policy` 一并落地）。

## 机制（举报）

- **举报人身份**：注册用户 → `reporter_id`，游客 → `reporter_guest_id`，匿名 401（复用 HTTP 层 `currentAuthor`）。
- **校验**：`target_type ∈ {comment, danmaku, drama, comment_image}`、`target_id > 0`、`reason ∈ {attack, vulgar, illegal, minor, ad, spoiler, other}`、`detail` 清洗后 ≤500 字。对象是否真实存在不在提交时校验（后台举报队列三角验证），`target_id` 直接存。
- **24 小时去重**：键为「举报人 + target_type + target_id」（复用 `dedupKey`，TTL 24 小时的 `cache.Dedup`）。窗口内重复举报同一对象：幂等放行、**不**重复落库，一律 204（不暴露「你已举报过」）。
- **后台队列（§25）**：`GET /api/admin/reports` 页码分页，状态 / 对象类型 / 原因精确筛选（空串不筛），Q 用 ILIKE 匹配说明或举报人用户名（模式转义 `\ % _`）；举报人注册用户显示昵称、游客显示「游客」。`POST /api/admin/reports/:id/handle` 把状态置为 `resolved`（已处理）或 `rejected`（已驳回）并存处理说明，记审计 `report.handle`。处罚举报人 / 被举报人（改账号状态）依赖用户管理（§26），本切片不含。

## 机制（表情）

- **前台下发**：`GET /api/v1/emojis` 一次返回全部表情包（含表情，只给 `code` / `image`）。按响应内容派生弱 ETag、`Cache-Control: public, max-age=0, s-maxage=86400, stale-while-revalidate=60`（强缓存 1 天；表情改动后内容哈希变化即失效，比绑定 `site.version` 更即时）。
- **后台维护**：`http/admin/community` 的 `RequirePage("emojis")` 下，`GET` 列表 + 包 / 表情 CRUD；写操作记审计（`emoji_pack.create/update/delete`、`emoji.create/update/delete`）。表情码形如 `[微笑]`（regex `^\[.+\]$`）、全局唯一（唯一约束冲突 → 409）；包名去空白 1–32 字；图片去空白 1–500 字。删包级联删其表情。
- **权限与导航**：迁移 00039 把「表情管理」挂到「社区」组、加 `emojis.view` / `emojis.edit`。因 00005 删除 / 转化了内置非超管角色，迁移不对具体角色授权——超管（is_super）自动拥有，自定义角色由运营在「权限矩阵」授予（与 resource_warm 等 00005 之后新增页面一致）。
- **admin 页面**：`/emojis` 以可展开的表情包承载层级（包 → 包内表情网格，含图片预览与坏链占位），而非平铺矩阵；每个输入 / 文本域都有中文 placeholder，表单用 zod 校验，只读角色控件禁用并给原因。
