# S3-11 订单与支付框架

进度：切片 1（订单数据模型、领域规则、sqlc 查询、PG 事务仓储、加密订单 API、development 模拟完成）已完成；本轮未运行全量构建、测试或 `go vet`。真实渠道适配、周期关闭任务、回调留痕与对账仍待实现。

## 目标

建立不依赖具体支付渠道的会员订单底座：订单快照、幂等创建、待支付数量限制、状态机、超时关闭、到账入账事务、回调留痕与我的订单读接口。真实渠道创建支付动作、验签、查单、退款与链上监听分别由 S3-12、S3-13、S3-14 完成。

## 范围

| 范围内 | 范围外 |
| --- | --- |
| `pay_order`、`pay_notify_log`、`payment_channel` 数据模型与索引 | 支付宝 RSA2、微信 APIv3、USDT 链上适配 |
| 会员套餐快照、订单号、幂等键、待支付订单上限 | 真实支付跳转、二维码、SDK 参数、商户凭据配置页面 |
| `pending → paid / closed`、`paid → refunded` 状态机 | 退款执行、补单、后台会员人工调整与对账页面 |
| 原子入账：订单、`user_vip`、`vip_ledger`、后续事件入队 | APP 商店内购收据校验 |
| 超时关闭任务、订单查询和我的订单读接口 | Web 真实购买页与 APP 支付 UI |

## 已确定的约束

1. S3-10 的五种 `vip_plan` 种子均为 `off`，价格为 0；本任务不猜测价格，也不开放购买。
2. `payment_channel` 初始全部停用且没有凭据；production 在没有已启用且已适配的渠道时拒绝创建订单。development 可显式启用模拟订单，但模拟不读取凭据、不调用第三方且该完成路径不在 production 注册。
3. 当前采用策略 A：S3-10 的套餐列表只按客户端过滤；本任务创建 `payment_channel` 后保存地区/客户端开关，S3-15 后台配置与 S3-12～14 渠道适配完成后才对套餐返回实时可用渠道。
4. 回调不进入 `/api/v1`，位于 `/callback/pay/*`，不经报文加密或用户会话；原文只做信封加密留存，不记录到日志。
5. 订单和入账必须在同一事务内完成；到账之后再失效 `xsite:vip:<uid>`，避免支付成功后仍读到旧权益。
6. River 框架虽未在任务表标记 S0-8 完成，但现有 API/worker 已真实使用事务内入队与周期任务；本任务复用该模式，不引入新队列框架。

## 数据与规则

- `pay_order.order_no`：16 字节随机值 base32 编码，唯一且不可推测。
- `product_snapshot`：下单时固化套餐 code、天数、金额、币种和渠道；后续改价不影响已有订单。
- 同一用户最多保留 3 笔未过期的 `pending` 订单；订单默认 30 分钟后关闭。
- 状态机：`pending → paid|closed`、`closed → paid`（迟到账，标记 `late=true`）、`paid → refunded`。
- 会员入账：`to_expire = max(from_expire, now) + duration_days`，写一条只追加 `vip_ledger(reason=purchase)`；并发入账通过同一用户会员行的事务锁串行化。
- 幂等：`Idempotency-Key` 在用户维度唯一；`(channel, channel_trade_no)` 唯一约束防止重复渠道通知入账。
- `payment_channel.credential_enc` 预留信封加密字段；本任务不写、读或记录任何支付凭据。

## 接口

| 接口 | 本任务职责 |
| --- | --- |
| `POST /api/v1/pay/orders` | 注册用户下单；校验套餐、渠道、幂等键、待支付上限；已启用适配器才返回对应 `pay_action` |
| `GET /api/v1/pay/orders/:order_no` | 仅查询本人订单，供前台轮询 |
| `POST /api/v1/pay/orders/:order_no/cancel` | 仅关闭本人尚未支付的订单 |
| `GET /api/v1/me/orders` | 游标分页读取本人订单 |
| `/callback/pay/*` | 仅注册通用接线与留痕边界；渠道验签实现留给 S3-12～14 |

## 切片

1. **订单数据模型与领域状态机**：迁移、订单领域规则与待生成 sqlc 查询已完成；事务仓储将在持有同用户 advisory lock 后锁套餐/渠道/会员行，完成套餐快照、会员叠加和流水。验收：并发入账不丢天数；同一订单不能二次入账。
2. **用户端订单 API**：创建、查询、取消、我的订单，契约和错误路径。验收：同一幂等键返回同一订单；第 4 笔待支付被拒。
3. **周期关闭与回调留痕**：River `pay` 队列、关闭任务、通用通知记录。验收：到期订单关闭；重复通知只留下可审计记录且不重复入账。
4. **渠道适配衔接**：由 S3-12～14 实现各自 `pay_action`、验签、查单与对账；S3-15 完成后台渠道配置与人工操作。

## 验收与风险

- 当前切片不创建真实支付；没有实际价格、已启用渠道和适配器时，购买接口必须安全拒绝。
- 支付回调原文、令牌、凭据和完整 IP 不得进入日志或响应。
- 代码完成后再在用户允许的时间窗口运行 `sqlc`、目标包测试、OpenAPI 校验、迁移和真实 HTTP 验收。


## Development 模拟支付（已接线）

- 仅 `APP_ENV=development` 的 API 注入 mock 订单服务，并注册 `POST /api/v1/pay/orders/:order_no/mock-complete`；production 不注册该路由，`POST /api/v1/pay/orders` 也会拒绝无真实适配器的订单。
- 模拟下单仍锁定同一用户、套餐和渠道，写入真实 `pay_order.product_snapshot`；模拟完成仍锁订单与 `user_vip`、更新状态、叠加到期时间、写 `vip_ledger` 并失效会员缓存。
- 模拟不调用第三方、不读取/写入支付凭据、不写 `pay_notify_log`，不能替代渠道验签、主动查单、回调原文加密或对账。
- development 下支付渠道的 `enabled=false` 仅对模拟订单放宽；套餐仍必须已上架、价格非零、允许所选客户端和渠道。生产始终按真实渠道可用性执行。
