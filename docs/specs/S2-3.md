## 机制

### 观看历史合并写（高频写、低写放大）
客户端每 15 秒 / 暂停 / 切集时 `POST /api/v1/me/history`（支持批量，单次 ≤ 100 条）。服务端不直接落库，而是先写 Valkey 单个 Hash `xsite:history:pending`，field = `<uid>:<drama_id>`，value = 紧凑 JSON 断点 `{"e":分集ID,"n":集号,"p":位置秒,"d":时长秒,"t":上报unix秒}`。**合并写**：同一（用户, 剧）的重复上报覆盖为最新，把一轮内的多次上报压成一次落库。

worker 的 `history_flush` 周期任务每分钟经 `drainHash`（`cache/drain.go` 的 Lua：原子 `RENAME` pending→taken + `PEXPIRE` + `HGETALL`）取出整批，批量 `UPSERT` 落库。**不丢不重**：任务编号作落库标识（token），UPSERT 失败不清 taken、由 River 重试同一任务；UPSERT 本身幂等（`ON CONFLICT (user_id,drama_id) DO UPDATE ... WHERE excluded.updated_at > watch_history.updated_at`，只在上报时间更新时覆盖，避免乱序上报把新进度盖回旧值）。

- **暂停记录**：`ReportHistory` 先查 `user.history_paused`，开了就静默忽略（既尊重开关，也防客户端绕过）。
- **伪造剧防护**：`ReportHistory` 只校验 `drama_id>0`，不校验存在性；落库 SQL `JOIN drama` 过滤掉不存在的剧，避免客户端上报伪造 `drama_id` 时外键失败把整批 UPSERT 卡死、让 worker 无限重试。
- **删除同步**：删历史（`DELETE ?drama_ids=`）/ 清空（`?all=1`）时同步清掉 Valkey 里尚未落库的断点，避免又被 worker 落库重现。
- 续播列表 `GET /api/v1/me/history` 读数据库（`JOIN drama` 取卡片字段：剧名、竖版封面、更新至 N 集；回收站中的剧不展示），最近在前，上限 500 条。断点精度按 `position_sec` 原样存取，15s 粒度由客户端上报节奏决定、服务端不做二次取整。

### 收藏 / 点赞（幂等）
`follow`（每人每剧一行）、`"like"`（剧 / 分集，`target_type` ∈ {drama, episode}，`target_id` 按类型多态、不建外键）。写用 `ON CONFLICT DO NOTHING` 幂等；收藏不存在的剧经外键失败映射 400（`dbErr` 23503→引流用户态错误）。删除幂等（未收藏 / 未点赞也 204）。

### 资料（S2-3 基本校验）
`GET /api/v1/me/profile` 读头像 / 昵称 / 简介及 `*_status`；`PATCH` 只改请求体中出现的字段（指针语义：缺省不动，空串清空）。校验：昵称去控制字符、折叠空白、≤ 40 字；简介去控制字符（保留换行）、逐行折叠、最多 2 个换行、≤ 80 字；头像引用 ≤ 500 字、无控制字符。`*_status` 恒为 `ok`（审核随 S2-9）。SQL 用 `COALESCE(sqlc.narg(...), col)` 实现 PATCH。

### 登录态 `GET /api/v1/me/state`
SPA / APP 加载时的轻量端点：返回 `{user:{id,nickname,avatar}, unread}`。`unread` 来自 `notification` 的未读部分（部分索引 `WHERE is_read=false`）。走 `RequireUser`：未登录 401，客户端据此判定为游客。

### 站内信 `GET/POST /api/v1/me/notifications`
GET 倒序游标分页（`?before=<id>&limit=`，1–50，缺省 50）；POST 全部标记已读。来源由后续里程碑产出。

## 验收

- `11` 的「续播断点 15s 粒度准确」：本机真实容器端到端——`POST /me/history` 上报 `{drama_id, episode_id=101, episode_number=3, position_sec=42, duration_sec=90}` → Valkey `xsite:history:pending` 出现 `57:41727 = {"e":101,"n":3,"p":42,"d":90,"t":...}`（紧凑格式、断点精确）→ worker `history_flush` 落库（日志 `观看历史已落库 rows=1`）→ `watch_history` 行 `57|41727|101|3|42|90`、Valkey pending 清空 → `GET /me/history` 返回该项并带 `JOIN drama` 卡片字段（title=E2E剧、cover、latest_episode=8）。`DELETE ?all=1` 后列表空；缺 `drama_ids`/`all` 返回 400。
- 其余端到端：`GET /me/state`（id + 未读数）、`GET/PATCH /me/profile`（PATCH 保留 2 个换行、`*_status=ok`）、`POST/DELETE /me/follow`（DB `follow` 增删）、`POST/DELETE /me/like`（`"like"` 增删、非法类型 400）、`GET/POST /me/notifications`（空列表 / 204）。
- 单测：`domain/me`（收藏 / 点赞校验、历史暂停跳过 / 批量上限 / 非法条目跳过、`FlushHistory` 解析 + UPSERT + 失败保留 taken、删除 / 清空同步 Valkey、通知上限收敛）；`domain/user`（资料基本校验：简介超长 / 换行过多 / 头像超长 400、昵称折叠、PATCH 指针语义、空 PATCH 回读）；`jobs`（`HistoryFlushWorker` 用任务编号作 token、失败重试、`ConfigureMe` nil 不注册）；`http/public/me`（各路由状态码 + 关键字段 + PATCH 指针语义 + 新路由受 `RequireUser` 保护）。
- 集成：`store/pg`（收藏 / 点赞幂等 + 外键 400 + 多态点赞；观看历史合并写「老上报不覆盖、新上报覆盖」+ JOIN 跳过伪造剧 + 软删剔除 + 删除 / 清空 + 暂停开关；资料读写 PATCH nil 不改 / 空串清空）；`store/cache`（历史合并写取出 / 同 token 重试 / `Clear` / `ClearAll`）。
- 回归：`go build ./...`、`go vet ./...`、`go test ./...` 通过（`store/pg` 的 `TestSiteRepo_Blocks` 偶发排序 flaky 属 S3-1 `MissingDramas` 查询、与本任务无关，复跑通过）。

## 假设（需确认）

1. **profile 的 S2-3/S2-9 边界**：`docs/11` S2-3 列了 `profile` 端点，`docs/13` 第 10.4 节把昵称保留词 / 改名频率、简介屏蔽词 / 引流、资料审核归 S2-9。本任务按后者：S2-3 的 profile 只做基本清洗 + 长度（昵称 ≤ 40、简介 ≤ 80），不做保留词 / 改名频率 / 屏蔽词 / 审核；`NICKNAME_LIMITED`、`CONTENT_REJECTED` 留给 S2-9 加入 `errs`。
2. **观看历史 Valkey 结构**：单 Hash `history:pending`（field=`<uid>:<drama_id>`）而非 `docs/03` 第 6 节字面的「`hset history:{uid}`」逐用户 Hash。单 Hash 可直接复用 `ad_count_flush` 的 `drainHash`（原子 RENAME + token 重试、不丢不重）；逐用户 Hash + 脏集合在 flush 重试时有竞态（drain 后 SREM 会丢掉新上报的 uid）。清空用 `HGETALL` 按 `<uid>:` 前缀过滤（pending 为分钟级小窗口，量大后再改 `HSCAN`）。
3. **续播列表上限 500 条**、通知列表单页 50 条：按 `docs/13` 第 2.2 节「注册用户最近 500 部」；超出淘汰的清理任务（`docs/13` 第 9 节）未在本任务实现。
4. **写接口限流**：`/me/*` 写接口（history/follow/like）目前只有 history 的单批 ≤ 100 + 合并写去重，未接每用户限流桶；按通用限流 S0-7 统一接入（与现有其他写接口一致）。
5. **me/state 身份字段**：返回 `id + nickname + avatar + unread`，不含 username（展示用昵称 / 头像，username 是登录名、客户端登录时已拿到）。
