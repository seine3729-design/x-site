# 0010 MPEG-TS HLS 转封装 Profile

状态：已采纳
日期：2026-10-26

## 背景

既有转封装链路已具备 H.264/AAC、多码率、AES-128、对象存储副本、CDN 选线和 Web ABR，但新产物为 2 秒 CMAF/fMP4（`init.mp4` + `.m4s`），清晰度阶梯为 360/540/720/1080。当前产品需要以 MP4 上传后产出 HLS 的 M3U8 + TS 分片，并把网络自适应聚焦在 360p、480p、720p。

直接替换历史目录会破坏长缓存的内容哈希对象，也会让正在播放的旧清单失效；向不明确的 CDN 厂商 API 直推又会混淆「对象写入源」与「CDN 读取线路」的安全边界。

## 决策

1. 新转封装统一使用 HLS MPEG-TS、H.264 + AAC-LC、固定 4 秒切片，输出 360p/480p/720p。
2. 切片通过 Go 做 AES-128-CBC 加密并以密文哈希命名；FFmpeg 不接触内容密钥。无音轨源补本地生成的静音 AAC。
3. 产物继续写入 `storage_settings` 选定的视频主 `storage_provider`，再由 `media_replica` 复制到镜像；CDN/`storage_line` 只从存储源回源、签名与缓存，绝不作为浏览器写端点。
4. 清单改写、目录前缀签名、试看裁剪、预热和跨源复制同时支持新 `.ts` 与历史 fMP4 `.m4s`/`EXT-X-MAP`。每次重转仍使用新的任务目录，只有成功后才切换分集引用。
5. 选择 4 秒而非 5–6 秒，减少起播首片字节数；360p 起播档约为 `(400k + 96k) × 4 / 8 ≈ 248 KB`，高于旧 2 秒 profile，因此保留 `startLevel=0`、CDN 长缓存和预热，并将默认每清晰度预热数从 3 调为 2（约 8 秒）。

## 备选方案与放弃原因

1. **保留 CMAF/fMP4**：已有链路性能更优，但不满足 M3U8 + TS 的兼容目标。
2. **固定 6 秒切片**：回源请求更少，但 360p 首片约 372 KB，弱网起播风险更高。
3. **保留 540p/1080p 并额外加入 480p**：编码、存储与 CDN 预热开销更高，且当前目标只要求覆盖低、中、高三档。
4. **直接上传某 CDN 媒资 API**：不同厂商的认证、清理、回源和成本语义不一致；未指定厂商前不能安全实现。现有对象存储 + CDN 回源模型已满足内容分发。

## 影响

- 不新增数据库迁移、接口路径或前端文案；`/api/v1/hls` 的清单内容由 fMP4 更新为 TS，因此 OpenAPI 版本和接口说明同步更新。
- 已有 fMP4 分集继续播放；存量重转是后续可控的运营任务，不在本次改造内。
- CDN 必须为 `.ts` 返回 `video/mp2t`，并保持切片缓存键排除 URL 鉴权参数、`Cache-Control: public, max-age=31536000, immutable`。
- APP 的回环代理尚未实现；本决策保证其未来可消费标准 AES-128 TS HLS，但不把文档设计当作已交付的原生播放功能。
