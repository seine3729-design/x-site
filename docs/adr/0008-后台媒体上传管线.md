# 0008 后台媒体上传管线

状态：已采纳
日期：2026-10-25

## 背景

运营后台此前只保存封面、配图和视频的手填资源路径或 URL，没有统一的文件选择、格式约束、进度反馈或视频转码入口。浏览器不能取得对象存储写入凭据；同时直接把大视频读进 API 内存会破坏服务稳定性。存储配置同时包含源站 `storage_provider` 与读取线路 `storage_line`，不能将 CDN 读域名误作对象写端点。

## 决策

- 新增受后台会话、CSRF、用途权限和所有者绑定的 `admin_media_upload` 上传会话；对象 key 仅由服务端生成。
- 后台以同源 `PUT /api/admin/uploads/{id}/content` 流式写入，不向浏览器下发存储凭据。上传会话仅 15 分钟有效，Content-Type 与 Content-Length 必须与申请信息一致。
- 创建会话时按媒体用途选取 `storage_settings` 配置的图片或视频主 `storage_provider`，并快照 endpoint、region、bucket、path style 与 `path_prefix`。后续变更同一 provider 的物理连接配置只影响新会话；旧会话继续使用快照目标和当前 provider 的加密写凭据，凭据本身不入会话。
- 图片统一压缩到最长边 2400 px、编码为 WebP（AVIF 的 canvas 编码主流桌面浏览器不支持，前台 AVIF 改由 CDN 分发层实时转，见 docs/08）；服务端在完成阶段重新核对大小、MIME 和文件头。最终 key 位于 `img/<purpose>/`。压缩由上面那条的服务端优化服务执行，浏览器 canvas 只作兜底 —— 固定一个高质量值在 canvas 上重编码，对已经优化过的 JPEG 几乎必然既掉画质又涨体积（运营看到的就是「压缩后比原图还大」），兜底路径因此改成沿质量阶梯取第一个确实小于原图的结果。
- 视频原始文件**只写私有 `MEDIA_SOURCE_BUCKET` 的 `ingest/` 前缀**，不写主存储，复用既有加密 MPEG-TS HLS 转封装；新分集产物写入 `video/episodes/<episode_id>/<job_id>/`（产物仍写主存储，它要经 CDN 分发）。源文件是 `private, no-store`、不进 CDN，唯一的读者是转码 worker（`transcode_job.source_key` 就是暂存 key），主存储里那一份没有任何代码路径会读；为它多付一次完整上行会直接把上传拖垮 —— 实测 30 MB 切 4 片并发传 Cloudflare R2 时单个 `UploadPart` 在途超过两分钟被对端断连、重试用尽后整个请求 500，改为只写入库桶后同样的 30 MB 用 0.2 秒。完成阶段只 `Head` 核对暂存对象的大小与类型；更早版本留下的会话（源文件在主存储）才退回复制一次。`Init` 仍然选取并快照视频主存储的 provider（`provider_id` 决定 `ingest/` 下的前缀，产物最终也要写它）。
- 图片压缩放在**服务端**（`POST /api/admin/images/optimize`，调 Tinify），浏览器只负责把原图交上去、拿回 WebP 再走三步上传。优化服务的 API Key 不下发浏览器（Tinify 也不支持浏览器直连的 CORS）。没配 Key、额度用尽或图片无法识别时接口返回 503/400，浏览器按质量阶梯用 canvas 兜底，不阻塞运营上传。
- 后台图片一律通过 `GET /api/admin/images/preview?key=` 同源代理显示。不让前端自己拼 CDN 地址：那要求图片线路配好且公开读（曾经出现过主存储一条线路都没有的情况），还得给运营 `storage_lines.view` 权限；代理只依赖图片主存储本身，一个地址适用于所有模块，代价是后台预览的流量过一次 service（后台图都是百 KB 级、并发极低，可接受）。
- 广告视频复用码率阶梯与 MPEG-TS HLS 打包能力，但不写分集内容密钥；产物写入 `video/assets/<upload_id>/master.m3u8`，上传会话保存其处理进度与最终 key。
- 历史外部 URL 与以 `/` 开头的路径仍可读取，后台新建媒体字段只由上传组件生成 `img/` / `video/` key。

## 备选方案与放弃原因

1. **浏览器直传对象存储预签名 URL**：当前存储源模型没有为浏览器写入提供可达的 S3 API 域名和 CORS 策略；直接复用读线路会把 CDN/只读端点误用于写入。
2. **通过 JSON 或 multipart 把完整文件交给 API**：会让视频进入默认 1 MiB 请求体限制，或促使 API 缓冲大文件。
3. **将广告视频伪装成分集转码任务**：分集任务硬绑定 `episode_id`、内容密钥和播放鉴权，复用会错误地暴露或污染分集状态。
4. **会话只保存 provider_id**：运营可在 15 分钟会话中修改 bucket、前缀或端点，完成与清理将按新配置访问，可能遗漏旧对象或写到错误目标；因此必须快照物理目标而非仅固定 provider 编号。

## 影响

- 新增 `admin_media_upload` 表、后台上传 API、广告视频 River 任务和统一 React 上传组件；迁移 `00044` 为会话增加物理存储目标快照。
- API 对上传内容路径单独放宽请求体中间件，但在处理器内按已登记的精确大小流式转发，其他接口仍维持 1 MiB 默认限制。
- 写入凭据只在受信任的 API 上传代理与 worker 内存中使用；浏览器、前台和 APP 永不获得凭据。CDN/`storage_line` 仅负责后续读取的域名、签名与选线。
- 新产物使用 `img/`、`video/` 前缀；历史 `hls/` 与 `posters/` key 不迁移，按数据库记录继续读取。
- 后续若让自定义主存储直接承接浏览器上传，应另行扩展存储源的浏览器写端点与临时 CORS 策略，不能把读凭据或写凭据交给客户端。

## 生命周期补充

上传内容写入前必须通过条件更新原子领取会话（`created → uploading`），因此同一会话的第二个 PUT 不会覆盖对象。对象写入后若状态更新、文件头校验或入队失败，处理器立即删除该对象（视频连带删除 `ingest/` 暂存）并将会话标记为 `failed`；worker 每小时回收过期未完成会话。视频只写私有入库桶，没有配置 `MEDIA_SOURCE_BUCKET` 时上传直接失败，不回退去写主存储；完成阶段发现暂存对象缺失（更早版本的会话或已被清理）时才退回从主存储复制一次。已就绪图片只删除会话记录，分集视频源保留给既有转码重试；广告转码成功或终态失败时先删除私有 `ingest/` 暂存，provider 原视频由过期会话清理回收。一个存储源清理失败不会阻塞同批其他会话，失败的会话记录保留给后续重试。
