# 08 · 性能优化方案

本文给出四端统一的性能目标、视频链路设计和各端优化清单。目标值是上线验收标准，压测与线上监控按第 8 节执行。

## 1. 性能预算

| 指标 | 目标（P75 / 4G 中端机，除注明外） | 采集方式 |
| --- | --- | --- |
| Web LCP | ≤ 2.0s | RUM（`web-vitals` 上报 `/api/v1/events`） |
| Web INP | ≤ 200ms | RUM |
| Web CLS | ≤ 0.05 | RUM |
| Web 首屏 JS | ≤ 90 KB（br） | CI 构建体积检查 |
| 首帧（起播） | P50 ≤ 1.0s，P95 ≤ 2.5s | 播放 QoS 埋点 |
| 卡顿率 | 每 10 分钟卡顿 ≤ 2s | 播放 QoS 埋点 |
| APP 冷启动到可交互 | ≤ 1.5s | APM |
| APP 刷剧滑动帧率 | ≥ 58fps（60Hz 屏） | 帧耗时埋点 |
| API 读接口 | P99 ≤ 150ms（源站） | OTel |
| API 写接口 | P99 ≤ 300ms | OTel |
| 选源接口 | P99 ≤ 80ms | OTel |
| 后台首屏 JS | ≤ 200 KB（br） | CI 构建体积检查 |

超出预算的 PR 在 CI 中标红，需要说明原因后才能合并。

## 2. 视频链路（对首帧影响最大）

### 2.1 封装与码率

- 新上传统一转为 **MPEG-TS HLS**：主清单 + 各档 M3U8 + `.ts` 切片，固定 **4 秒**。GOP 与切片对齐，强制关键帧、闭 GOP 并重复 SPS/PPS，让每片可独立起播；历史 CMAF/fMP4 产物继续按数据库记录播放，不批量替换。
- 码率阶梯（竖屏 9:16）：

| 档位 | 分辨率 | 视频码率 | 用途 |
| --- | --- | --- | --- |
| 起播档 | 360×640 | 400 kbps | 首切片固定用这一档，弱网优先出画面 |
| 标清 | 480×854 | 850 kbps | 普通移动网络 |
| 高清 | 720×1280 | 1.6 Mbps | 网络稳定时自动升档或用户手选 |
| 超清 | 1080×1920 | 3.0 Mbps | Wi-Fi / 用户手选 |

- 表中码率是上限：x264 CRF 23 加码率上限（VBV 缓冲 1 秒，限制起播切片体积），简单画面实际码率更低。档位按短边计算，横屏、方屏同样适用（如横屏起播档为 640×360）；只出不超过源短边的档位，源比 360 还小时按源尺寸出一档；帧率超过 30 时减半。主清单 `BANDWIDTH` 为实测峰值（RFC 8216 定义），`AVERAGE-BANDWIDTH` 为平均值，各档按码率从低到高排列，播放器默认从起播档开始（S1-5b）。
- 编码：H.264 作为兼容档；HEVC（iOS/新 Android）作为高效档，同画质约省 30–40% 流量；AV1 视终端解码能力占比再评估。本 profile 只出 H.264。
- 音频：AAC-LC 96 kbps；源为单声道时保持单声道，无音轨源补双声道静音 AAC，保证新产物均为 H.264 + AAC。
- 封面与首帧图：每集生成首帧 WebP（AVIF 待评估），用作 `poster`，在视频出画面前先显示，主观等待更短。

### 2.2 分发

- 切片由 CDN 直接回源对象存储，业务进程只签发清单与密钥（见 `03` 第 4.2 节）。
- 清单与密钥 `Cache-Control: no-store`（含签名与令牌，经加密接口下发，加密响应一律不缓存；S1-8 的清单原文在服务端 Valkey 读穿缓存 1 小时，改写只做签名，300 个切片的直连存储预签名约 12ms）；切片 `public, max-age=31536000, immutable`（地址按内容哈希）。
- **CDN 的缓存键必须排除鉴权参数**（`hmac_token` 的 `p`/`exp`/`s`、SigV4 的 `X-Amz-*`）。切片地址按内容哈希命名、内容不可变，鉴权参数只决定「这次请求有没有权限」，不决定「拿到的是哪个对象」；把它们算进缓存键，`exp` 每轮换一次就是一个新键，上面那条 `immutable` 长缓存与预热都无从谈起。各厂商的 URL 鉴权默认就是这个行为，接入时逐条确认。
- 预热任务（S4-5）提前把**切片**拉到边缘；**清单进不了边缘**（上面那条 `no-store`），预热清单热的是服务端那层清单原文读穿缓存，省掉回源读清单那一跳。默认每个清晰度预热前 2 个 4 秒切片（约 8 秒），热门剧与新上架剧在上架前各热一轮。
- 开启 HTTP/3（QUIC）与 TLS 1.3 0-RTT（仅对幂等 GET 切片），弱网与移动网络切换下更稳。

### 2.3 客户端起播策略

1. 列表/刷剧流中，下一条只预取清单 + 起播档首个 4 秒切片（360p 含音频约 248 KB，上限随实际码率变化）。
2. 起播先用起播档，ABR 按实时吞吐与缓冲自动升到合适档位。
3. 记录上次测得带宽，下次 `startLevel` 直接用对应档位。
4. 测速只在首次进入或连续卡顿时执行，结果缓存 10 分钟。
5. 同时活跃的解码器 ≤ 3（Web `<video>` / APP 控制器池）。

## 3. 边缘与缓存

| 层 | 内容 | 策略 |
| --- | --- | --- |
| CDN 边缘 | 静态资源、切片、封面 | 长缓存 + 内容哈希 |
| CDN 边缘 | SSR 页面（首页、列表、详情） | `s-maxage` 60–120s + `stale-while-revalidate` 300s；缓存键不含登录态（含语言前缀，天然按语言区分） |
| CDN 边缘 | 文案 `i18n/*/<标签>.<hash>.json` | 内容哈希 + `immutable`；只有 `manifest.json` 短缓存（`04` A.4.3） |
| CDN 边缘 | 用户端 JSON 接口 | **不缓存**：报文加密后每个响应的密钥都不同（`10` 第 5.3 节），一律 `no-store`；由 BFF 与后端缓存承担，客户端用 ETag 拿 304 |
| BFF | 站点配置、SSR 用到的公共数据 | 内网明文调用，进程内缓存 + ETag 条件请求，`version` 变化即失效 |
| 后端 L1 | 进程内 LRU | 秒级 TTL，热点详情、配置、屏蔽词 |
| 后端 L2 | Valkey | 分钟级 TTL，列表、榜单、计数；客户端缓存（RESP3 tracking）减少网络往返 |
| 后端 L3 | PostgreSQL | 索引覆盖查询、只读副本承载列表与看板 |

- 防击穿：`singleflight` 合并同键回源；防雪崩：TTL ±10% 抖动；防穿透：空值缓存 30s。
- 个性化数据（追剧状态、续播、未读）与公共页面分开请求，公共部分才能边缘缓存。
- 清缓存同时清边缘（按缓存标签或路径前缀）。

## 4. 后端（Go）

- **运行时**：Go 1.27.3（Green Tea GC 默认）；`GOMEMLIMIT` 设为容器内存 85–90%；容器感知 `GOMAXPROCS`；PGO 用线上 profile 构建，热点路径通常可再提 2–7%。
- **JSON**：`encoding/json/v2`，大响应流式编码（`jsontext.Encoder`）；列表接口只返回卡片需要的字段。
- **数据库**：
  - pgx 连接池 `MaxConns` = 核数 × 4 起步，经 PgBouncer transaction 模式；pgx 用 `QueryExecModeCacheDescribe` 兼容 PgBouncer。
  - 批量写用 `pgx.Batch` 或 `COPY`（埋点、续播、计数落库）。
  - 列表用游标分页；`hot` 排序依赖表达式索引或冗余列 `hot_score`（定时刷新）。
  - 看板与列表查询走只读副本；PG 18 异步 I/O（`io_method=worker` 或 `io_uring`）提升顺序扫描与 VACUUM。
  - 计数类（播放、点赞）先进 Valkey `INCR`，每分钟合并落库，避免热点行锁。
- **并发**：每个外部调用都带 `context` 超时；对象池只用于明确的高频大对象（`sync.Pool` 用于缓冲区）。
- **网络**：回源与内部调用用 HTTP/2 长连接；响应压缩交给 CDN，源站只对未经 CDN 的内部流量压缩。
- **任务**：重活（转封装、体检、预热、汇总）全部在 worker 进程，API 进程不做 CPU 密集工作。
- **报文加密**：每请求一次 X25519 解封装 + 两次 AES-GCM，约数十微秒；`apienc` 缓冲整个响应后加密，流式响应（SSE 等）不放在 `/api/v1` 加密组。加密响应不再压缩，列表接口靠游标分页与字段裁剪控制体积。
- **福利写路径**（`13` 第 9 节）：签到、抽奖、领取、兑换都是单事务、固定语句数，写 P99 ≤ 300 ms（抽奖 ≤ 150 ms）；限时抢兑用 Valkey Lua 闸门防超卖；任务事件与图片处理进 worker 队列；金币流水按月分区。
- **失去边缘缓存后的容量**：APP 的公共读请求全部回源，由进程内 LRU → Valkey → PG 承担；压测（X5-3）按「APP 读请求 100% 回源」评估，热门公共数据（首页编排、榜单、站点配置）优先在进程内命中。

## 5. Web（SvelteKit + Bun）

- SSR + 边缘缓存；首屏只渲染可视区块，其余区块按可视懒挂载。
- hls.js、二维码、海报、弹幕发送面板、评论抽屉全部动态导入。
- 图片：CDN 实时转 AVIF/WebP，按显示尺寸取对应档位；Web 端用 `BlobImage` 转临时 `blob:` 显示（不加密，`04` C.8）。`fetch` 要等 JS 执行后才开始：首屏前 4 张标 `priority`（立即、高优先级），LCP 大图在 `<head>` 用 `<link rel="preload" as="fetch" crossorigin>` 预加载，其余进入可视区 300px 内再取；LCP 超预算时首屏首图可回退普通 `<img>`。
- 报文加密：浏览器每个 `/api/v1` 请求多一次 X25519 与 HKDF（Web Crypto，约 1 ms 内）；列表渲染路径上不要串行发多个加密请求。
- 多语言：只随 SSR 下发当前语言文案（每种 2–4 KB），其他语言不进客户端包。
- 视频：hls.js 统一走 MSE（含 iOS 17.1+ ManagedMediaSource），清单与密钥多一次加解密（毫秒级），首帧预算不变。
- 字体：系统字体栈；如需品牌字体，子集化 + `font-display: swap`。
- 运行时：Bun 1.4 空闲 CPU 与内存占用更低；动态压缩不用同步 API 阻塞事件循环（交给 CDN 或流式压缩）。现用 `node:zlib` 流式压缩器（线程池，Brotli 质量 5）。不要用 `CompressionStream('brotli')`：Bun 下它没有质量参数，输出与质量 11 完全相同，压一个首页约 19 ms（质量 5 约 0.2 ms，体积只大 12%）且在主线程，50 个并发时事件循环卡住约 0.85 s。实测（本地生产构建首页，3000 请求 / 50 并发，各 4 轮）：同步压缩改流式后吞吐约 3.1k → 3.7k 次/秒，P50 15.5 → 13.0 ms，P99 30.7 → 25.4 ms，响应字节不变。
- 预取：链接 `data-sveltekit-preload-data="hover"`（桌面）/ `"tap"`（移动端），刷剧流预取下一条元数据。
- 第三方脚本延后到 `requestIdleCallback`；广告位固定尺寸占位。

## 6. APP（Flutter）

- **启动**：首页骨架与上次缓存数据同步渲染；网络、RASP、推送注册并行且不阻塞首帧；非首屏插件延迟初始化。
- **渲染**：Impeller 默认；避免在滚动项中使用 `saveLayer`（`Opacity`、`ClipRRect` 改用预裁剪图片或 `DecoratedBox`）；列表项 `const` 构造、`RepaintBoundary` 隔离播放器层。
- **状态**：Riverpod `select` 精细订阅，进度条等高频更新只重建自身。
- **图片**：按显示尺寸解码（`memCacheWidth/Height`），内存缓存上限按设备内存动态设置。
- **计算**：JSON 大响应、drift 查询、加解密放到后台 Isolate（`Isolate.run`）。
- **播放**：控制器池 ≤ 3；离屏立即暂停；低端机（内存 < 4 GB）关闭下一条预加载画面，只预取清单。
- **网络**：native adapter 走系统栈（HTTP/2/3、连接复用）；请求合并（启动时一次拉配置 + 首页）。
- **包体**：R8、资源裁剪、按 ABI 拆包、图片资源 WebP；`--split-debug-info` 去掉符号。

## 7. 后台（React）

- React Compiler 自动记忆化；路由级分割；表格虚拟滚动；URL 驱动的服务端分页。
- 重组件（富文本、图表、CSV 解析、拖拽）懒加载；CSV 解析放 Web Worker。
- Query 缓存分级：字典类 10 分钟、列表 30 秒、看板 5 分钟。

## 8. 压测与监控

- **压测**：k6 脚本覆盖首页、详情、选源、清单、续播上报、评论写入；目标 = 日峰值 × 3。每次大版本发布前在预发环境执行。
- **RUM**：Web Vitals、首帧、卡顿、错误按端/地区/运营商/线路/CDN 维度看。
- **APM**：OTel 链路 + 持续 profiling；慢查询（> 100ms）自动记录执行计划（`auto_explain`）。
- **告警**：首帧 P95、选源失败率、API P99、DB 池等待、Valkey 命中率、River 积压超阈值即告警。
- **回归**：CI 记录构建体积与关键接口基准（Go `testing.B`），较主干退化 > 10% 时阻断合并。
