> 状态：按 `deploy/prod/` 的实际文件编写，边缘层、压缩、CDN 链路已在本地按生产拓扑实测
> 最后核对：2026-10-26
> 权威范围：从「代码还在本机」到「三个域名可访问」的完整操作顺序

## 0. 这份文档和 `deploy/prod/README.md` 的分工

| 看哪一份 | 什么时候 |
| --- | --- |
| **本文** | 按顺序做一遍。第一次部署、换服务器、新人接手 |
| [`deploy/prod/README.md`](../deploy/prod/README.md) | 查某个机制为什么这么设计、某个文件干什么用、排查具体故障 |

本文不重复 README 里的原理说明，只给顺序、命令和验收点。遇到「为什么」就去 README 对应章节。

整条链路：

```
本机                      GitHub                         服务器
────                      ──────                         ──────
git push ───────────────► main 分支
                            │
                            ├─ ci.yml        PR 上跑四端检查（合入前的闸门）
                            │
                            └─ deploy.yml    ① 构建 8 个镜像 → 推 GHCR
                                             ② 从镜像里取静态产物 → 传 Cloudflare R2
                                             ③ SSH ──────────────► tar 同步 deploy/prod
                                                                   docker compose pull
                                                                   admintool migrate
                                                                   compose up -d
                                                                   nginx -s reload
                                             ④ 对外 curl 验活
```

全流程只有一处人工输入：服务器上的 `.env`。镜像、产物、配置文件都由流水线送过去。

## 1. 准备清单

开始之前先把这些拿到手，中途缺一项就得停下来等。

| 项目 | 要求 | 备注 |
| --- | --- | --- |
| 服务器 | Linux x86_64，≥ 4 核 8 GB，≥ 100 GB 磁盘，root 或 sudo | 自带 PostgreSQL + Valkey + 转封装，内存给少了转封装会被 OOM |
| 公网端口 | 80/tcp、443/tcp、**443/udp**、22/tcp | 443/udp 是 HTTP/3，云厂商安全组里也要放 |
| 域名 | `duanju66.cc`、`admin.duanju66.cc`、`feedback.duanju66.cc` | 托管在 Cloudflare（R2 自定义域已经在这个 zone 下） |
| Cloudflare 账号 | 能改 DNS、SSL/TLS 模式、Cache Rules | 用户端域名要走代理模式 |
| R2 | 桶 + 自定义域 + 一对访问密钥 | 当前是桶 `duanju666` + `cdn.duanju66.cc`，已可用 |
| GitHub | 一个仓库（私有即可）+ 能配 Secrets | 镜像推到同账号的 GHCR，不用额外注册镜像仓库 |
| 本机 | git、ssh、openssl | 构建不在本机做，不需要 Docker |

> **架构约定（已定，不用再选）**：静态资源域名固定 `https://cdn.duanju66.cc`；`admin` 与 `feedback` 的带哈希产物走 R2；`apps` 不用独立资源域名，而是把 `duanju66.cc` 整体挂到 Cloudflare 代理后面。原因见 README 第 4 节。

## 2. 第一步：把仓库推上 GitHub

工作区现在还不是 git 仓库（`git rev-parse` 报 not a repository），所以这一步是从零开始。

### 2.1 推之前必须确认的三件事

**(1) 忽略规则是否够用。** 这个仓库里躺着 1.5 GB 的依赖和构建产物，忽略规则漏一条，第一次提交就会把几百兆推上去，之后再想清掉只能重写历史。核对方式——在工作区**之外**建一个 git 目录做干跑，不在工作区留 `.git`：

```bash
cd ~/Desktop/x-site
D=/tmp/gitprobe/.git; rm -rf /tmp/gitprobe; mkdir -p /tmp/gitprobe
git --git-dir=$D --work-tree=$PWD init -q
git --git-dir=$D --work-tree=$PWD add -A
git --git-dir=$D --work-tree=$PWD diff --cached --name-only | wc -l       # 期望 1600 上下
git --git-dir=$D --work-tree=$PWD diff --cached --name-only -z \
  | xargs -0 du -ch | tail -1                                            # 期望 20 MB 以内
git --git-dir=$D --work-tree=$PWD diff --cached --name-only \
  | grep -E 'node_modules|/dist/|\.next/|\.svelte-kit|/build/|\.env$'     # 期望没有输出
rm -rf /tmp/gitprobe
```

实测结果：**1635 个文件、18 MB**。被挡在外面的：各端 `node_modules`（合计 1.1 GB）、`feedback/.next`（159 MB）、`mobile/build`（78 MB）、`service/tmp`（107 MB）、`admin/dist`、`apps/build`、`apps/.svelte-kit`、根目录 `.env`、`.local/`、`semantic-review/`、`__pycache__/`，以及所有 `.br` / `.gz` 预压缩产物。

> 为这次上传补过三处忽略规则，换环境时注意别丢：
> - `admin/.gitignore` **原来根本不存在** —— 不加会提交 `admin/node_modules`（380 MB）。
> - `service/.gitignore` 加了 `/worker`、`/_uiseed` 等 `go build` 留下的裸二进制（两个就 49 MB）。**刻意没有 `/api`**：gitignore 分不清同名的文件和目录，写上会把契约目录 `service/api/`（`openapi.yaml` 在里面）一起忽略掉。
> - 根 `.gitignore` 加了 `semantic-review/`、`__pycache__/`。

**(2) 有没有密钥混在里面。** 扫一遍源码与配置（跳过 `docs/`，那里引用关键词本身会自己命中）：

```bash
grep -rIl --exclude-dir=node_modules --exclude-dir=.git --exclude-dir=docs \
  -e 'PRIVATE KEY-----' -e 'AKIA' -e 'cfat_' \
  service apps admin feedback mobile deploy .github *.yaml *.sh 2>/dev/null
```

预期没有输出。几点说明：

- `.env.example` 与 `deploy/prod/.env.example` 里只有占位值，是故意提交的。
- `compose.yaml` 里的 `${XXX:?...}` 是变量引用，不是值。
- 真正的 `.env` 已被忽略（第 (1) 步的干跑已验证）。

**(3) 行尾与大文件。** 仓库里没有需要 Git LFS 的文件（最大的是 808 KB 的图标数据集）。

### 2.2 初始化并首次推送

```bash
cd ~/Desktop/x-site

git init -b main
git add -A
git status --short | head -20          # 再扫一眼，确认没有意外条目
git commit -m "chore: 初始化仓库（四端 + 生产部署）"

# GitHub 上先建一个空仓库（不要勾选 README / .gitignore / license，否则要先 pull）
git remote add origin git@github.com:<账号>/x-site.git
git push -u origin main
```

推完**不会**触发部署：`deploy.yml` 虽然监听 `push: branches: [main]`，但此时 Secrets 还没配，流水线会在登录镜像仓库那步失败。这是预期的，先把第 3、4、5 步做完再重跑。

### 2.3 分支保护（不是可选项）

`deploy.yml` 的触发条件是「推到 main 就发布」，而 `ci.yml` 监听的是 `branches-ignore: [main]` 与 `pull_request`。
**这意味着直接推 main 会跳过全部检查直接上线。** 唯一的闸门是分支保护，必须配：

Settings → Branches → Add rule，`main`：

- ☑ Require a pull request before merging
- ☑ Require status checks to pass before merging → 勾上 `service`、`apps`、`admin`、`feedback`、`deploy-config`
  （这些检查名第一次开 PR 跑过之后才会出现在列表里，先建 rule 再回来补）
- ☑ Require branches to be up to date before merging
- ☑ Do not allow bypassing the above settings

配好之后 main 上的每个提交都经过了 CI，「推 main 即发布」才是安全的。

## 3. 第二步：配置 GitHub

### 3.1 生成部署专用 SSH 密钥

不要复用个人密钥。在**本机**生成一对只用于部署的：

```bash
ssh-keygen -t ed25519 -C "x-site-deploy" -f ~/.ssh/xsite_deploy -N ""
```

公钥装到服务器（第 4 步建好账号后做）：

```bash
ssh-copy-id -i ~/.ssh/xsite_deploy.pub deploy@<服务器IP>
```

拿到服务器的主机密钥指纹——工作流刻意不用 `StrictHostKeyChecking=no`（那等于接受任何冒充服务器的主机）：

```bash
ssh-keyscan -H <服务器IP> 2>/dev/null
```

### 3.2 Secrets（Settings → Secrets and variables → Actions → Secrets）

| 名称 | 值 | 怎么拿 |
| --- | --- | --- |
| `DEPLOY_HOST` | 服务器 IP 或主机名 | |
| `DEPLOY_USER` | `deploy` | 第 4.2 节建的账号 |
| `DEPLOY_SSH_KEY` | `~/.ssh/xsite_deploy` 的**全部内容** | `cat ~/.ssh/xsite_deploy`，含首尾的 BEGIN/END 行 |
| `DEPLOY_KNOWN_HOSTS` | `ssh-keyscan -H <IP>` 的输出 | 多行一起粘 |
| `R2_ACCOUNT_ID` | Cloudflare 账户 ID | 用来拼 S3 endpoint |
| `R2_ACCESS_KEY_ID` | R2 访问密钥 ID | R2 → Manage API tokens |
| `R2_SECRET_ACCESS_KEY` | R2 机密访问密钥 | 只在创建时显示一次 |

`GITHUB_TOKEN` 不用配，Actions 自动注入。推 GHCR 和服务器拉镜像都用它（工作流把这个临时令牌经 SSH 传给服务器登录，用完 `docker logout`，服务器上不长期存放仓库凭据）。

> R2 密钥给的权限按「只能读写这一个桶」最小化。如果这对密钥曾经出现在聊天、工单或任何日志里，先在 Cloudflare 上轮换再配进来。

### 3.3 Variables（同一页的 Variables 标签）

| 名称 | 值 | 必填 |
| --- | --- | --- |
| `DEPLOY_PATH` | `/opt/xsite` | 否（默认就是这个） |
| `R2_BUCKET` | `duanju666` | 是 |
| `APPS_DOMAIN` | `duanju66.cc` | 否（只用于发布后的对外验活） |
| `ADMIN_DOMAIN` | `admin.duanju66.cc` | 否（同上） |
| `FEEDBACK_DOMAIN` | `feedback.duanju66.cc` | 否（同上） |
| `CDN_BASE` | `https://cdn.duanju66.cc` | **否** —— 不设就是这个默认值，只在换域名时才设 |

变量用 Variables 而不是 Secrets：它们会出现在构建日志里（资源前缀要能对账），本来也不是秘密。

### 3.4 Environment

Settings → Environments → New environment，名字必须是 `production`（`deploy.yml` 里写死了）。

可选但建议：勾 **Required reviewers**，这样每次发布前需要人点一下确认。内容平台改动频繁的话先不开，等上线稳定后再加。

### 3.5 GHCR 包的可见性

第一次推送镜像后，GitHub 会在账号下创建 8 个 package（`x-site/service`、`media-worker`、`postgres`、`edge`、`certbot`、`apps`、`admin`、`feedback`）。默认继承仓库可见性。保持**私有**即可——服务器用工作流下发的临时令牌拉取，不需要公开。

## 4. 第三步：服务器初始化

以下命令在服务器上执行。示例是 Debian 13 / Ubuntu 24.04，其他发行版换包管理器。

### 4.1 系统基础

```bash
# 时间必须准：证书校验、JWT 过期、TOTP 二次验证都看系统时间
sudo timedatectl set-timezone UTC
timedatectl   # 确认 "System clock synchronized: yes"

# 8 GB 内存建议配 4 GB swap：转封装峰值会吃内存，宁可变慢不要被 OOM 杀掉
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 4.2 部署账号与 Docker

```bash
sudo adduser --disabled-password --gecos "" deploy
```

Docker 用官方 apt 源装（发行版自带的 `docker.io` 跟不上 compose v2 的特性）。
**刻意不用 `curl https://get.docker.com | sh`**：那是把一个远程脚本直接交给 root 执行，
拿不到任何校验，装生产机不该这么做。官方源的步骤是固定的四步：

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/debian $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

> Ubuntu 把上面两处 `debian` 换成 `ubuntu`。

```bash
sudo usermod -aG docker deploy
sudo systemctl enable --now docker
sudo -iu deploy docker compose version   # 必须是 v2.x
```

把第 3.1 节的公钥装进 `/home/deploy/.ssh/authorized_keys`。顺手收紧 SSH：

```bash
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/'               /etc/ssh/sshd_config
sudo systemctl reload ssh
```

### 4.3 防火墙

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 443/udp      # HTTP/3。漏了这条浏览器会静默退回 HTTP/2
sudo ufw enable
```

**不要**放开 5432 / 6379。compose 把 PostgreSQL 绑在 `127.0.0.1`，Valkey 完全不映射端口。

> Docker 会直接写 iptables，`-p 0.0.0.0:xx` 的端口映射能绕过 ufw。本项目只有 nginx 映射到 `0.0.0.0`（80/443），数据库那条写的是 `127.0.0.1:...`，所以不受影响。新增端口映射时留意这一点。

### 4.4 目录与配置

```bash
sudo mkdir -p /opt/xsite/geoip
sudo chown -R deploy:deploy /opt/xsite
```

服务器上的最终布局（`prod/` 这一层由工作流在解包时去掉）：

```
/opt/xsite/
├── compose.yaml        每次发布由工作流覆盖
├── .env                只有这一个文件是人工维护的，工作流不会碰它
├── scripts/            deploy.sh、gen-secrets.sh、r2-setup.sh…
├── nginx/  certbot/    镜像构建用的源文件（服务器上不直接用，同步过来便于排查）
└── geoip/              放 ip2region.xdb，挂进 service 与 worker
```

**`.env` 要在第一次发布之前就位**，否则 `deploy.sh` 会停在「找不到 .env」。从本机推过去最省事：

```bash
# 本机执行
scp -i ~/.ssh/xsite_deploy deploy/prod/.env.example deploy@<IP>:/opt/xsite/.env
```

然后在服务器上生成密钥并填值：

```bash
cd /opt/xsite
chmod 600 .env
# 14 个密钥字段，每个独立随机值（不要一个值填到所有字段）
./scripts/gen-secrets.sh
```

脚本只打印、不自动写入——直接覆盖会把已填的其他字段冲掉。把输出粘进 `.env` 替换对应行，然后补齐这些**脚本生成不了**的字段：

| 字段 | 填什么 |
| --- | --- |
| `IMAGE_PREFIX` | `ghcr.io/<账号>/x-site`（全小写） |
| `APPS_DOMAIN` / `APPS_ALIASES` / `ADMIN_DOMAIN` / `FEEDBACK_DOMAIN` | 四个域名 |
| `CERTBOT_EMAIL` | 证书到期提醒邮箱 |
| `DATABASE_URL` / `DATABASE_RO_URL` | 把上面生成的 `XSITE_APP_PASSWORD` / `XSITE_RO_PASSWORD` 填进连接串 |
| `VALKEY_URL` / `APPS_VALKEY_URL` | 把 `VALKEY_PASSWORD` 填进去。0 号库给后端、1 号库给 BFF，刻意分开 |
| `S3_ENDPOINT` / `S3_ACCESS_KEY` / `S3_SECRET_KEY` / `S3_BUCKET_*` / `MEDIA_SOURCE_BUCKET` | 媒体对象存储（`docs/12`）。`MEDIA_SOURCE_BUCKET` 不能等于公开读的 `S3_BUCKET_ASSETS`，启动校验会拒 |
| `EDGE_TRUST_CLOUDFLARE` | 用户端域名走 Cloudflare 代理就保持 `1` |

填完跑一次自检，再做结构校验：

```bash
cd /opt/xsite
./scripts/check-env.sh                                    # 空值、密钥重复与长度、production 约束、文件权限
docker compose --env-file .env config >/dev/null && echo "compose 解析通过"
```

`check-env.sh` 只报字段名、不打印任何密钥值。它查四类问题：

| 查什么 | 为什么 |
| --- | --- |
| 必填项为空 | `compose config` 也能查，但一次只报一个字段 |
| 还留着模板里的占位值 | 比留空更隐蔽：`example.com`、`填上面的密码`、`ghcr.io/example` 看起来像个值，`compose config` 也能解析过去，要到「连不上数据库」「证书邮件发给 example.com」才暴露 |
| 密钥字段共用同一个值 | 最常见的错是生成一个值粘到所有字段。那样一把泄露等于全部泄露，轮换任何一项都要同时动其他所有项 |
| 密钥长度与 `引用:密钥` 格式 | 后端启动校验要求 ≥ 32 字符，格式不对会直接启动失败 |
| `MEDIA_SOURCE_BUCKET` 等不等于 `S3_BUCKET_ASSETS` | 私有入库桶不能是公开读的那个，启动校验会拒 |
| 两个 Valkey 库是否撞号 | 后端用 /0、BFF 用 /1；撞号会让两边的限流计数互相干扰 |
| `TRUSTED_PROXIES` 是否为空 | 空的话后端不采信边缘层转发的客户端 IP，限流全按边缘层那一个地址算 |
| `.env` 权限是否 600 | 644 意味着同机任何账号都能读到全部密钥 |

`docker compose config` 查的是结构（所有 `${X:?...}` 必填项是否齐），查不出「值写错」。剩下的格式校验在后端启动时做：`production` 会拒绝 http 的 `ADMIN_ORIGINS`、拒绝 `AUTO_MIGRATE`、拒绝关闭报文加密、拒绝开启 `EGRESS_ALLOW_PRIVATE`。

### 4.5 GeoIP（可选，影响按地区选线）

把 ip2region 的 `ip2region.xdb` 放到 `/opt/xsite/geoip/`。没有这个文件时地区一律按未知处理，只有 `region_scope=global` 的兜底线路会命中——功能不挂，但多线路调度失效。

## 5. 第四步：DNS 与 Cloudflare

### 5.1 DNS 记录

| 记录 | 类型 | 值 | 代理 |
| --- | --- | --- | --- |
| `duanju66.cc` | A | 服务器 IP | **代理（橙云）** |
| `www` | A | 服务器 IP | **代理（橙云）** |
| `admin` | A | 服务器 IP | 直连（灰云）或代理都行 |
| `feedback` | A | 服务器 IP | 直连或代理都行 |
| `cdn` | — | R2 自定义域，已存在 | Cloudflare 自动管理 |

用户端域名必须走代理——`apps` 的静态资源靠边缘缓存加速，不用独立资源域名（README 第 4 节解释了为什么不能用）。

### 5.2 代理模式下要改的三处

1. **SSL/TLS → Overview → 加密模式选 `Full (strict)`**。源站上的 Let's Encrypt 证书正好满足。选 Flexible 会让 Cloudflare 用 HTTP 回源，源站的 HTTPS 跳转会把请求打成死循环。
2. **`.env` 里 `EDGE_TRUST_CLOUDFLARE=1`**。否则客户端 IP 全是 Cloudflare 边缘节点，限流与风控把所有访客当成同一个来源。打开后边缘层只信任 `deploy/prod/nginx/snippets/cloudflare-ips.conf` 里的 22 个网段再取 `CF-Connecting-IP`。网段会变，升级边缘层镜像时顺手 `./scripts/update-cloudflare-ips.sh` 看一眼 diff。
3. **Caching → Cache Rules 加两条**：
   - `URI Path starts with /_app/immutable/` 或 `/icons/` → Eligible for cache，Edge TTL「Use cache-control header」（源站已给 `immutable` 一年）。
   - 确认**没有**任何规则把 HTML 设成可缓存。SSR 页面随登录用户变化，缓存串号会把别人的页面发出去。Cloudflare 默认不缓存 HTML，这条是防止后来有人加了 "Cache Everything"。

ACME 挑战不受代理影响：Cloudflare 不会把 `/.well-known/acme-challenge/` 强制跳 HTTPS。

### 5.3 R2 一次性设置

在**本机**跑（需要 aws cli；没装就用 `docker run --rm -v "$PWD":/w -w /w amazon/aws-cli` 代替 `aws`）：

```bash
cd ~/Desktop/x-site/deploy/prod
R2_ENDPOINT=https://<账户ID>.r2.cloudflarestorage.com \
R2_BUCKET=duanju666 \
AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... \
APPS_DOMAIN=duanju66.cc APPS_ALIASES=www.duanju66.cc \
ADMIN_DOMAIN=admin.duanju66.cc FEEDBACK_DOMAIN=feedback.duanju66.cc \
CDN_DOMAIN=cdn.duanju66.cc \
  ./scripts/r2-setup.sh
```

这一步**必须做**，不是优化项：后台与反馈社区的入口脚本是 `<script type="module">`，而模块脚本一律按 CORS 模式取（这是规范行为，不是可选项）。R2 不回 `Access-Control-Allow-Origin` 的话，这两个站一行脚本都跑不起来。品牌 Logo 也从这个域名取，白名单漏了就是全站没图标。

`put-bucket-cors` 是**整体替换**。这个桶同时放媒体资源（`img/`、`video/`、`static/` 前缀），所以脚本里把 CDN 域名自己也列进了白名单。加域名时改脚本重跑，不要在控制台手改——下次跑脚本又会被覆盖回去。

脚本同时设了生命周期：`admin/`、`feedback/` 前缀下的对象 90 天过期（发布时不删远端旧产物，靠这条清理），以及未完成的分片上传 1 天后中止。

## 6. 第五步：第一次发布

### 6.1 触发

Actions → Deploy → Run workflow（分支 `main`，`deploy` 勾选），或者往 main 推一个提交。

### 6.2 流水线在做什么

| 任务 | 内容 | 大致耗时 |
| --- | --- | --- |
| `prepare` | 算出镜像前缀（GHCR 要全小写）、标签（git SHA 前 12 位）、CDN 地址 | 秒级 |
| `backend`（5 个并行） | `service`（distroless，含 api/worker/admintool）、`media-worker`（带 FFmpeg）、`postgres`（PG 18 + pg_bigm）、`edge`（Alpine nginx + ngx_brotli）、`certbot` | 首次 6–10 分钟 |
| `apps` | 构建并推送。**不接独立 CDN**，产物自带 `.br`/`.gz` | 3–5 分钟 |
| `frontend`（2 个并行） | `admin`、`feedback`：带 CDN 前缀构建 → `--load` 到本地 → 从镜像里拷出静态产物 → **校验必须有 `.br`**（没有就失败）→ 传 R2 → 再推镜像 | 4–8 分钟 |
| `deploy` | 同步 `deploy/prod` → 临时令牌登录 GHCR → `deploy.sh <tag>` → 对外验活 | 2–4 分钟 |

几个刻意的顺序：

- **产物先上 R2，镜像后推**。反过来会出现「镜像已发布但 CDN 上没有它要的脚本」。
- **静态产物是从刚构建出来的镜像里拷的**，不是另外构建一遍。两次构建的内容哈希对不上的话，页面会去 CDN 取一个不存在的文件名，而且只在生产复现。
- 服务器上 `deploy.sh` 的顺序是 **拉镜像 → 迁移 → 起服务 → 重载 nginx → 验活**。先迁移是因为 production 禁用 `AUTO_MIGRATE`；最后重载 nginx 是因为开源版 nginx 只在启动/重载时解析 upstream 里的服务名，容器重建后不重载会一直 502。

### 6.3 第一次一定会看到的现象

**「对外验活」会失败，这是预期的。** 顺序是这样的：

1. nginx 要证书才能起来，而证书要 nginx 先起来才能过 ACME 挑战。`nginx/entrypoint.sh` 用自签证书占位打破这个死循环，日志里是「暂用自签证书占位，等 certbot 签发」。
2. certbot 这时才去签发。拿到之后由 nginx 的重载循环换上（默认 6 小时一轮）。
3. 这中间 `curl` 会因为证书不受信而失败。

不想等就手动推一下：

```bash
cd /opt/xsite
docker compose --env-file .env logs certbot | tail -20     # 确认已签发成功
docker compose --env-file .env restart nginx               # 立刻换上真证书
curl -sI https://admin.duanju66.cc/ | head -3
```

certbot 签发失败时**不会重试风暴**，退避 1 小时再试（Let's Encrypt 对验证失败有每小时 5 次的限制，硬撞会把账号锁在外面）。常见原因：DNS 还没生效、80 端口被云厂商安全组挡了、Cloudflare SSL 模式选错。

> 想先演练整条流程又不占 Let's Encrypt 的正式额度：`.env` 里设 `CERTBOT_STAGING=1`，
> 签出来的证书不受浏览器信任，但流程完全一致。演练完改回 `0`，再把证书卷清掉让它重新签：
>
> ```bash
> cd /opt/xsite
> docker compose --env-file .env down nginx certbot
> docker volume rm xsite-prod_letsencrypt xsite-prod_edge_certs
> docker compose --env-file .env up -d
> ```

### 6.4 创建首个超级管理员

后台没有注册入口，第一个账号只能用命令行建。密码从标准输入读，不会出现在命令行参数、进程列表和 shell 历史里：

```bash
cd /opt/xsite
read -rs -p "密码（8–128 位）: " PW && echo
printf '%s\n' "${PW}" | docker compose --env-file .env \
  run --rm -T --entrypoint /app/admintool service create-admin -username root -role superadmin
unset PW
```

`-T` 关掉 TTY 分配：管道喂 stdin 时 compose v2 大多能自己判断，但在 SSH 会话里不加会偶发失败。

账号初始状态是 `unused`，首次登录后变 `active`。角色编码 `superadmin` 是唯一内置角色，其余角色在后台新建。

### 6.5 验收清单

```bash
# 服务器上
cd /opt/xsite
docker compose --env-file .env ps                                   # 全部 running / healthy
docker compose --env-file .env exec service /app/api -healthcheck    # 退出 0（distroless 里没有 curl）
docker compose --env-file .env exec nginx ls /srv/admin/current      # 后台静态产物已就位
docker compose --env-file .env exec nginx ls /srv/feedback/current   # 反馈社区静态产物已就位
```

```bash
# 本机：外部可访问性
curl -sI https://duanju66.cc/api/v1/health            # 200
curl -sI https://admin.duanju66.cc/                   # 200
curl -sI https://feedback.duanju66.cc/                # 200
curl -sI https://www.duanju66.cc/                     # 301 → https://duanju66.cc/
curl -sI http://duanju66.cc/                          # 301 → https

# 未知 Host 直接被断开（444），扫到源站 IP 的人拿不到站点指纹
curl -ksI --resolve 'notexist.example:443:<服务器IP>' https://notexist.example/   # curl: (52) empty reply

# 压缩：优先 br、回退 gzip
curl -sI -H 'Accept-Encoding: br, gzip' https://admin.duanju66.cc/ | grep -i content-encoding   # br
curl -sI -H 'Accept-Encoding: gzip'     https://admin.duanju66.cc/ | grep -i content-encoding   # gzip

# CDN：带哈希的产物 + CORS + 长缓存
curl -sI -H 'Origin: https://admin.duanju66.cc' \
  "$(curl -s https://admin.duanju66.cc/ | grep -oE 'src="[^"]*assets/[^"]+\.js"' | head -1 | sed 's/src="//;s/"//')" \
  | grep -iE 'HTTP/|access-control-allow-origin|cache-control|content-encoding'

# HTTP/3：浏览器开发者工具的「协议」列应显示 h3
```

后台登录一次、前台首页打开一次、浏览器控制台确认没有跨域或 CSP 报错，才算真的通了。

## 7. 日常：从改代码到上线

### 7.1 标准路径

```bash
git switch -c feat/xxx
# ... 改代码，本地用 ./dev.sh 验证 ...
git push -u origin feat/xxx
# GitHub 上开 PR → ci.yml 按改动路径跑对应的端 → 评审 → 合入 main
# 合入即触发 deploy.yml，全自动到上线
```

`ci.yml` 的 `changes` 任务用一次 `git diff` 判断改了哪些端，只跑受影响的检查。改 `deploy/` 或 `.github/workflows/` 会额外跑 `deploy-config`（校验生产 compose 能解析、nginx 模板能渲染并通过 `nginx -t`、部署脚本语法）。

### 7.2 几类改动的注意点

| 改了什么 | 要注意 |
| --- | --- |
| 只改前端样式/文案 | 没有额外动作。注意 `apps` 与 `feedback` 的首屏预算在 CI 里是硬闸门，`feedback` 最重的路由只剩 6.8 KB 余量 |
| 新增数据库迁移 | 必须写 `-- +goose Down`。发布时 `admintool migrate` 在服务启动前执行，失败就停住、旧版本继续跑 |
| 改接口 | 同步 `service/api/openapi.yaml` 与 `docs/07`（仓库红线） |
| 新增后端必填环境变量 | **先改服务器上的 `.env`，再合入代码**。顺序反了的话新容器起不来，而旧容器已经被替换 |
| 换 CDN 域名 | 要改四处：`CDN_BASE` 变量、`feedback/public/sw.js` 的 `ASSET_ORIGINS`（并把 `VERSION` 加一）、`feedback/src/app/layout.tsx` 与 `admin/index.html` 的 `preconnect`、`.env` 的 `IMAGE_BASE_URLS`，再重跑 `r2-setup.sh` 更新 CORS |
| 后台新增图片线路 | 同步 `.env` 的 `IMAGE_BASE_URLS` / `MEDIA_CONNECT_ORIGINS`，否则生产 CSP 会把封面和视频拦掉 |

### 7.3 回滚

镜像按 git SHA 打标签，回滚就是指回上一个标签：

```bash
cd /opt/xsite
docker images --filter "reference=ghcr.io/*/x-site/service" --format '{{.Tag}}'   # 看本机还有哪些版本
./scripts/deploy.sh <上一个标签>
```

要注意的两件事：

- **迁移不会自动回滚。** `admintool migrate` 只升不降。新版本加了列、旧版本读不认识的 schema 时，优先前滚修复而不是回滚；真要 `goose down` 得人工评估数据。
- `docker image prune` 只清没有任何标签的层，上一个版本的镜像会保留，所以回滚不需要重新拉取。

## 9. 排查速查表

| 现象 | 先看什么 |
| --- | --- |
| 流水线卡在 `deploy` 的 SSH 步 | `DEPLOY_KNOWN_HOSTS` 是否为空或和服务器实际指纹不符（换过机器/重装过系统都会变） |
| `deploy.sh` 报「找不到 .env」 | 第 4.4 节漏了，`.env` 不由工作流下发 |
| 整站 502 | nginx 在服务重建后没重载过。`dc exec nginx nginx -s reload` |
| 后台整站 404 | `admin-assets` 一次性容器没跑成功、卷是空的。`dc logs admin-assets` |
| 浏览器报证书不受信 | 还在用自签占位。`dc logs certbot` |
| 页面能开但脚本全 404 | `CDN_BASE` 和实际上传的前缀对不上。对比 HTML 里的地址与 `aws s3 ls` |
| 控制台报跨域、脚本一个都不执行 | R2 CORS 白名单里没有这个域名，重跑 `r2-setup.sh` |
| 后台登录后立刻掉登录态 | `ADMIN_ORIGINS` 和实际域名不一致（production 只允许 https） |
| 封面或视频出不来 | `IMAGE_BASE_URLS` / `MEDIA_CONNECT_ORIGINS` 没跟着后台线路表更新，被 CSP 拦了 |
| 资源还是 gzip、没有 Brotli | 先确认产物里有 `.br`；再看是不是哪个 location 误加/误删了 `proxy_set_header Accept-Encoding ""`（apps 那条必须**不清**、feedback 那条必须**清**，README 第 4 节） |
| 限流把正常用户拦住、日志里 IP 全一样 | 站点在 Cloudflare 后面但 `EDGE_TRUST_CLOUDFLARE` 不是 1 |
| 后台资源预热进度条不动 | SSE 被缓冲，确认 `/api/admin/` 的 `proxy_buffering off` 还在 |

## 10. 安全红线与当前缺口

红线（`docs/10`、`security-checklist`）：

- `.env` 只存在于服务器上，权限 600，不提交、不进镜像、不贴进聊天或工单。
- 密钥每个字段独立生成，用 `scripts/gen-secrets.sh`，不要一个值填到所有字段。
- 不放开 5432 / 6379 到公网；`TRUSTED_PROXIES` 不要写宽（写宽等于让任何人伪造客户端 IP）。
- `real_ip_header` 必须配合 `set_real_ip_from` 白名单，缺一不可。
- 存储源凭据由后台页面录入、信封加密入库、只写不读；不要塞进 `.env`。
- R2 密钥若曾经明文出现在任何可留存的地方，立即轮换。

当前缺口，上线前要知道：

- **没有自动备份。** PostgreSQL 的连续归档与定期全量要按 `docs/09` 单独配（`docs/11` X5-4）。现在只有第 8 节的手动 `pg_dump`。
- **单副本，发布有秒级中断。** `service` / `apps` / `feedback` 都是一个实例，`compose up -d` 会重建容器。要无缝发布得先上多副本 + 真正的负载均衡。
- **没有多 CDN 与 GSLB**（`docs/11` X5-1），也没有回源 mTLS、没有「源站安全组只放行 CDN」。
- **后端没有 `/metrics`**，`docs/11` 要求的仪表盘还没有数据源。
- **HTTP/3 只验到配置层**：指令在运行中的配置里、容器在 UDP 443 监听、`Alt-Svc` 正常下发，但真实 QUIC 握手没有端到端实测过（本机没有带 HTTP/3 的客户端）。上线后看浏览器开发者工具的协议列确认。
- **数据库与 Valkey 和应用同机。** 换托管实例只要改三个连接串（线上必须 `sslmode=verify-full` 与 `rediss://`），其余不动。
