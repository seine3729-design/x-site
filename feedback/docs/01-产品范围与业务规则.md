# 01 · 产品范围与业务规则

> 状态：草案（待产品确认）  
> 最后核对：2026-10-23  
> 权威范围：角色能力、功能优先级、反馈状态机与社区业务规则

## 1. 产品形态

Feedback 社区不是泛论坛，而是围绕“项目共创”组织内容：

```text
项目
├─ 项目主页：定位、测试状态、加入方式、入口
├─ 项目动态：公告、测试任务、上线小结、讨论
├─ 反馈：提交 → 分诊 → 计划 → 开发 → 验证 → 上线/关闭
├─ 议题：项目方发起的定向问题与结构化回答
└─ 成员：运营、维护者、测试成员与贡献记录
```

首页用于聚合项目与有价值的活动，不按纯发布时间无限堆叠内容。

## 2. 用户画像与核心任务

| 用户 | 主要动机 | 核心任务 |
| --- | --- | --- |
| 新加入测试者 | 知道测什么、快速开始 | 阅读置顶测试任务 → 加入项目 → 提交首条反馈 |
| 活跃贡献者 | 推动产品变好并看到影响 | 找到相似反馈 → 补充证据/投票 → 跟踪上线 → 查看贡献记录 |
| 产品运营 | 收集结构化洞察 | 发布动态/议题 → 分诊 → 回复 → 通知 → 发布小结 |
| 研发维护者 | 获得可复现信息 | 查看技术上下文 → 认领 → 更新状态 → 关联发布版本 |
| 社区版主 | 保持讨论安全有效 | 处理举报、隐藏敏感信息、限制滥用并处理申诉 |

## 4. 功能优先级

### 4.1 P0：MVP 必须有

- 项目目录、项目主页、动态列表与详情；
- 账号会话、项目加入和基础资料；
- 反馈提交、列表、详情、搜索、筛选、状态历史；
- 图片附件、评论、官方回复、关注与站内通知；
- 后台分诊队列、负责人、优先级、标签、合并重复项、状态与发布版本；
- 举报、内容隐藏、用户限制、审计日志；
- 公开/成员/私密三种可见性；
- 数据导出、账号注销和安全基线。

### 4.2 P1：首发范围内的闭环增强（用户已确认保留）

- 投票与按热度排序；
- 周期议题（自由回答/单选/多选）；
- 贡献值、贡献等级与采纳记录（非货币化，`adr/0005`）；
- 贡献榜（登录可见，用户可隐藏自己）；
- 相似反馈提示与重复项推荐；
- 项目健康与响应时效看板。

这些功能在 M3 交付，但属于首发范围，不是“以后再说”。它们会带来反作弊与运营成本，相应控制写在 `09` 第 12 节。

### 4.3 P2：验证价值后再做

- 成员自由发布讨论帖；
- 自定义反馈表单与自定义状态；
- Web Push 通知（无邮件通道，见 `adr/0007`）；
- 高级搜索服务、AI 摘要与聚类；
- 公开（免登录）贡献榜。

### 4.4 明确不做

- 多语言与语言切换；
- 邮件/短信/第三方 IM 通知；
- 与 GitHub、GitLab、Jira、飞书、Slack、Telegram 的集成或同步；
- 用户自助创建项目、开放自助注册。

## 5. 项目规则

### 5.1 生命周期

`draft → recruiting → active → paused → archived`

- `draft`：只对项目团队和平台管理员可见；
- `recruiting`：允许符合规则的用户申请或使用邀请加入；
- `active`：允许成员提交反馈并参与议题；
- `paused`：内容可读，暂停新反馈，页面必须显示原因与恢复预期；
- `archived`：只读，不再发送普通通知，不能物理删除历史反馈。

归档和恢复由项目所有者或平台管理员执行，必须审计。

### 5.2 可见性

| 值 | 可见对象 | 典型用途 |
| --- | --- | --- |
| `public` | 所有人 | 已公开项目、公告、非敏感建议 |
| `members` | 已加入项目的成员与项目团队 | 封闭内测内容 |
| `private` | 作者、项目团队、被明确授权的处理人 | 安全问题、账号问题、含个人数据的反馈 |

按角色展开的完整可见性矩阵见 `00` 第 8.2 节，它是实现和越权测试的权威依据。

可见性只能收紧或由有权限的运营明确放宽。把私密内容转公开前必须获得作者确认，并移除个人信息与敏感附件。

**项目创建**：只有平台管理员能创建项目并指定首位项目所有者。项目所有者之后可管理成员和（按授权）发放邀请码，但不能新建项目。注册必须持有效邀请码，访客无法自助注册。

## 6. 项目动态规则

动态类型：`announcement`（公告）、`test_task`（测试任务）、`changelog`（上线小结）、`discussion`（讨论）。

- 只有项目运营/维护者可发布前三类；`discussion` 是否允许成员创建为 `[待确认]`。
- 每个项目最多 3 条置顶动态；置顶必须有结束时间或人工取消。
- `changelog` 可关联一个发布版本及多条已上线反馈。
- 已发布动态修改后显示“已编辑”和更新时间；重大内容更改需保留审计差异。
- 删除采用软删除；已有互动的动态只能隐藏并说明原因，不能静默消失。

## 7. 反馈规则

### 7.1 类型

默认类型为：

| 类型 | 必填上下文 |
| --- | --- |
| `bug` Bug | 发生页面、复现步骤、实际结果、期望结果、环境信息 |
| `experience` 体验问题 | 使用场景、哪里受阻、期望改善 |
| `feature` 功能建议 | 要解决的问题、目标用户、期望结果；不强迫用户写解决方案 |
| `content` 内容/资源需求 | 需求内容、用途与优先原因 |
| `access` 无法访问/性能 | 页面、时间、地区到省级、网络类型、错误表现；不得要求精确位置 |
| `other` 其他 | 标题和说明 |

项目可禁用默认类型；项目级自定义类型属于 P2。

### 7.2 编号与编辑

- 每条反馈生成不可变项目内编号，如 `APP-1024`；合并后原编号仍可访问并跳转到主反馈。
- 作者可在 `submitted` 且尚无官方处理时编辑正文；进入 `triaged` 后只能追加补充，避免历史证据被改写。
- 作者可撤回自己的反馈；有官方处理记录时转为“作者已撤回”并保留最小审计，不直接物理删除。
- 提交必须接受幂等键，网络重试不能生成重复反馈。

### 7.3 状态机

主流程：

```text
submitted → triaged → planned → in_progress → verifying → shipped → closed
     │          │          │            │           │
     ├──────────┴──────────┴────────────┴───────────┼→ duplicate
     ├───────────────────────────────────────────────┼→ declined
     └───────────────────────────────────────────────┴→ closed

shipped / closed / declined ──(有新证据且获批准)──→ triaged
```

| 状态 | 用户可见语义 | 进入条件 | 可执行者 |
| --- | --- | --- | --- |
| `submitted` | 已收到，尚未确认 | 提交成功 | 系统 |
| `triaged` | 已确认并完成初步分类 | 类型、可见性、重复关系已检查 | 运营/维护者 |
| `planned` | 已进入计划，不承诺日期 | 有处理意图与负责人/目标版本之一 | 运营/维护者 |
| `in_progress` | 正在处理 | 有负责人 | 维护者 |
| `verifying` | 等待验证结果 | 方案已部署到可验证环境 | 维护者/运营 |
| `shipped` | 已随某版本上线 | 必须关联发布版本或上线说明 | 维护者/运营 |
| `closed` | 流程结束 | 已解决、作者撤回或无需继续 | 运营/维护者 |
| `duplicate` | 与已有反馈重复 | 必须关联主反馈 | 运营/维护者 |
| `declined` | 当前不采纳 | 必须给可公开原因 | 运营/维护者 |

规则：

- 每次状态变化写入不可变历史，记录操作者、时间、公开说明和内部原因；
- `planned`、`in_progress` 超过项目配置时限无更新，提醒负责人，不自动改状态；
- `shipped` 必须关联 `release_id` 或提供可验证的上线说明；
- 合并重复项时，原反馈的关注者自动关注主反馈，但可取消；
- 从终态重开必须说明新证据，计入审计并通知原参与者。

## 8. 优先级、标签与负责人

- 优先级：`critical / high / medium / low / unset`，只对项目团队与作者显示还是完全公开为 `[待确认]`。
- 严重度与优先级分开：Bug 严重度描述影响，优先级描述处理顺序。
- 一条反馈最多一个负责人，可设置协作者；无负责人时属于项目分诊队列。
- 标签由项目团队维护，颜色不能作为唯一含义；删除标签只解除关联，不删除反馈。
- 不因投票数自动提升优先级，投票只是决策输入之一。

## 9. 评论、回复与投票

- 评论默认按时间正序，一层回复；详情页可按“最早/最新”切换。
- 官方回复显示角色标识，但不能仅靠颜色区分。
- 评论发布后 15 分钟内允许作者编辑；编辑后显示时间。已有举报或被官方引用时禁止删除正文，只能申请隐藏。
- 每个成员对同一反馈最多一票；取消投票不删除审计汇总所需的反滥用记录。
- 自己的反馈默认关注；评论或投票不自动关注，避免意外通知。
- 禁止用投票结果承诺排期，排序需同时提供“最新”“最近更新”。

## 10. 附件规则

`[假设]` MVP 仅支持 JPEG、PNG、WebP，单文件 ≤ 10 MiB、每条反馈最多 6 张。

- 上传前提示用户遮盖账号、手机号、邮箱、订单号和密钥；
- 服务端检查真实 MIME、文件头、像素与解码结果，重新编码并删除 EXIF；
- 原图默认私有，公开反馈展示处理后的派生图；
- 附件下载使用短期授权地址，不把对象存储凭据暴露给客户端；
- 恶意或无法解码文件拒绝，扫描失败进入隔离区而非直接发布。

## 11. 议题规则

- 类型：`free_text / single_choice / multiple_choice`；
- 由项目运营创建，必须有开始时间、结束时间和可见性；
- 每个成员每个议题只有一份有效回答，可在截止前修改；
- 结果在投票前、投票后或结束后可见，由创建者预先选择，发布后不能改得更宽松；
- 自由回答走与评论相同的审核与举报规则；
- 删除议题改为关闭/归档，保留聚合结果与审计。

## 12. 通知规则

事件类型：官方回复、被提及、反馈状态变化、合并、关联版本上线、议题邀请、审核结果、安全事件。

- **只做站内通知**。账号不收集邮箱，没有邮件通道；Web Push 为 P2 可选（`adr/0007`）；
- 因为无法离线触达，站内通知必须有未读计数、持久列表和可追溯的历史，不能只用一次性 Toast；
- 聚合高频事件，避免每次投票都通知；
- 安全与账号事件不能关闭，其余通知支持项目级和事件级退订；
- 通知不包含私密反馈全文，只包含最小摘要与受保护链接；
- 读取通知失败不能阻塞核心反馈流程。

## 13. 贡献值与等级

用户已确认投票、议题和贡献等级进入首发（`adr/0005`）。M2 先积累采纳事实，M3 交付等级与贡献榜，全程非货币化。

事件与分值：

| 事件 | 分值建议 | 条件 |
| --- | ---: | --- |
| 有效反馈被确认 | +1 | 从 `submitted` 进入 `triaged`，每条一次 |
| 反馈被采纳并上线 | +4 | 进入 `shipped`，每条一次 |
| 补充证据帮助复现 | +1 | 运营明确标记，每条最多一次 |
| 议题回答被选为有帮助 | +1 | 每个议题最多一次 |
| 误判/撤销采纳 | 对应冲销 | 只追加反向账，不修改旧事件 |

- 不因发帖、评论、投票数量直接发分，减少刷量；
- 分值变更必须是不可变账本事件并带原因；
- 等级阈值由配置决定，但改阈值不改历史账；
- 用户可隐藏等级与公开署名；
- 不兑换现金或商品，不使用“金币”等可能暗示货币价值的命名，除非后续单独合规评审。

## 14. 内容治理与申诉

- 举报原因：垃圾信息、骚扰、人身攻击、隐私泄露、安全漏洞、违法内容、侵权、其他；
- 严重隐私/安全问题允许先隐藏后复核；普通争议不自动下架；
- 每次处理必须记录规则、证据摘要、操作人、期限和是否可申诉；
- 临时限制有明确到期时间，永久封禁需平台管理员确认；
- 用户能查看自己的处理结果并在时限内申诉；申诉不得由原处理人单独终审。

## 15. 验收场景

1. 访客可以浏览公开项目和公开反馈，但提交入口要求登录并保留回跳地址。
2. 成员提交 Bug 时缺少复现步骤会收到字段级错误；网络重试不会重复创建。
3. 私密反馈只被作者和有项目权限的团队成员读取，搜索和通知不泄露标题。
4. 运营把重复反馈合并后，原链接仍可访问，原关注者收到说明并转为关注主反馈。
5. `shipped` 状态没有发布版本或上线说明时保存失败。
6. 作者修改已分诊反馈时只能追加补充，不能覆盖原始正文。
7. 被隐藏内容显示规则与申诉入口；无权用户看不到内部备注与审计细节。
8. 贡献撤销通过反向事件完成，历史总分可重算且与显示一致。

## 16. 范围外与待确认

范围外见 `00` 第 4.2 节。开始 M1 前需确认多项目、邀请制、登录方式和可见性；开始投票/议题/贡献任务前需分别确认其是否进入 MVP。
