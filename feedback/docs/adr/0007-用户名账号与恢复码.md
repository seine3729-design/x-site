## 背景与问题

用户确定账号标识为用户名，且注册必须邀请码，同时不要求收集邮箱或手机号。这带来一个必须立刻解决的连锁问题：**没有外部联系方式，就没有标准的密码找回通道，也没有邮件通知通道。** 如果不明确定义，开发会默认实现“邮箱重置”，与决策冲突；或者干脆没有找回路径，用户忘记密码就永久失去贡献历史。

## 约束与决策驱动因素

- 平台是邀请制内测社区，用户规模可控，但贡献历史和署名对用户有长期价值；
- 不收集邮箱/手机符合数据最小化，也减少泄露面；
- 管理员直接重置用户密码等于可以接管任意账号，会破坏贡献署名的可信度；
- 账号找回必须防枚举，不能变成“输入用户名即可判断是否存在”的探测接口；
- 通知必须有可用渠道，否则状态变更无法到达用户。

## 决策

### 身份

- 账号标识为 `handle`（用户名），大小写不敏感唯一，3–32 字符，允许小写字母、数字、下划线和连字符，不允许仅数字或保留词；
- 密码使用 Argon2id，参数入库可升级；最小长度 12，允许粘贴与密码管理器，不强制字符组合；
- 不收集邮箱、手机号；用户可选填公开昵称与简介；
- 注册必须携带有效邀请码，邀请码只存哈希、限定项目/角色/期限/次数（`adr/0003`）。

### 找回

- 注册成功时生成一次性**恢复码**，只显示一次，要求用户确认已保存；数据库只存哈希；
- 恢复码用于自助重置密码：提交「用户名 + 恢复码 + 新密码」后重置成功，并撤销全部会话、生成新恢复码；
- 用户可在设置页重新生成恢复码（需当前密码），旧码立即失效；
- 恢复码验证失败统一提示且耗时相近，并按账号与来源分层限流；
- **管理员不能重置用户密码、不能查看恢复码。** 管理员只能停用账号、作废邀请或重新发放邀请，全部进入审计；
- 注册页与设置页必须明确告知：恢复码是唯一自助找回方式，丢失后账号无法恢复。

### 通知渠道

- 只实现站内通知；
- 不实现邮件通道；
- Web Push 为 P2 可选，取决于是否确有需求；
- 数据导出与注销结果通过站内通知 + 站内下载交付，不外发。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 完全不提供找回 | 实现最简单，但邀请制社区的贡献历史不可替代，用户丢密码即失去全部署名，支持压力会转移到管理员 |
| 邮箱绑定后邮件重置 | 与“只用用户名、不收集邮箱”的决策冲突，且需要邮件服务、退订和投递治理 |
| 管理员协助重置密码 | 管理员可接管任意账号，贡献署名与私密反馈的可信度被破坏；需要双人审批才能勉强缓解，成本高于恢复码 |
| 安全问题 | 答案易被猜测或遗忘，是已被淘汰的做法 |
| 仅 Passkey/WebAuthn | 安全性好，但设备丢失同样需要恢复路径，且与“用户名 + 密码”的明确要求不一致 |

## 正面后果

- 自助找回不依赖任何外部服务；
- 不收集联系方式，泄露面和合规成本更小；
- 管理员无法冒用用户身份，贡献署名可信；
- 通知范围明确，不会实现到一半才发现没有邮件通道。

## 负面后果与风险

- 用户可能不保存恢复码，丢失后账号不可恢复，需要在界面反复提示；
- 恢复码本身是高价值凭据，被窃取等于接管账号，必须限流与审计；
- 没有邮件意味着无法在用户离线时触达，重要状态变更只能等用户登录；
- 账号唯一标识是用户名，改名会影响署名与提及，需要限制频率。

## 安全、隐私与运维影响

- 恢复码：≥ 128 bit 随机，展示为分组字符串，只存哈希，重置后立即轮换；
- 恢复、登录、注册、改密统一防枚举，错误信息与耗时一致；
- 任一凭据变更都递增 `session_version`，使旧会话立即失效；
- 恢复、改密、停用、邀请作废写审计，且不记录凭据本身；
- 日志、埋点与错误上报不得出现用户名以外的身份信息或恢复码片段。

## 迁移、兼容与回滚

首期无存量账号。若以后决定支持可选邮箱（仅用于找回与安全提醒），按“新增可选字段 → 用户自愿绑定 → 双通道并存”推进，不改变用户名作为主标识；恢复码机制可保留为备用。若决定取消恢复码，必须先提供替代找回路径，不能直接删除。
