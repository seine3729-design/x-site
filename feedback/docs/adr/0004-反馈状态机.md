# 0004 · 反馈状态机

状态：已采纳  
日期：2026-10-23  
决策人：用户（2026-10-23 确认 P0 范围，未要求自定义工作流）  
适用范围：反馈、通知、贡献、发布版本、运营看板  
关联任务：D0-2、B2-2、A2-1  
取代/被取代：无

## 背景与问题

反馈社区的信任来自可理解、可追踪的处理过程。状态过少无法表达计划、开发和验证；状态过多或项目任意自定义会让用户困惑、统计失真并显著增加实现复杂度。

## 约束与决策驱动因素

- 用户需要知道反馈是否被看到、正在做什么以及是否已上线；
- `planned` 不能被误解为固定发布日期；
- 状态历史必须不可变并支持审计；
- 重复和拒绝需要原因；
- 上线应与发布版本或可验证说明关联；
- 首期跨项目指标应使用统一状态口径。

## 决策

首期使用固定状态：

`submitted → triaged → planned → in_progress → verifying → shipped → closed`

旁路终态：`duplicate / declined / closed`。`shipped / closed / declined` 可在有新证据且获授权时回到 `triaged`。

规则：

- 每次迁移写不可变历史，公开说明和内部原因分开；
- `triaged` 表示已完成基本分类，不等于接受解决；
- `planned` 明确“不承诺固定日期”；
- `in_progress` 必须有负责人；
- `shipped` 必须关联发布版本或上线说明；
- `duplicate` 必须关联同项目主反馈，原链接保留；
- `declined` 必须有可公开原因；
- 非法跨级变更默认拒绝，管理员也不能绕过领域规则；
- 首期项目不能自定义状态，只能配置显示名称的文案翻译。

## 备选方案与放弃原因

### 四态：已提交/已确认/开发中/已上线

简单但无法区分计划、验证、关闭、重复与拒绝，运营会滥用备注补语义。

### 完全自定义工作流

灵活但权限、迁移、统计、通知、集成和 UI 成本显著增加，不适合 MVP。

### 用标签代替状态

标签可多选且无迁移约束，无法形成可靠时效、历史和通知。

## 正面后果

- 用户和运营共享统一语义；
- 可计算各阶段停留时间与 SLA；
- 通知、贡献和版本关联触发明确；
- 后续与外部 Issue 状态可做映射。

## 负面后果与风险

- 某些项目流程可能觉得状态过细；
- 运营若不更新状态会暴露流程老化；
- 重开和回退需要清楚规则；
- 外部工具状态无法总是一一映射。

## 安全、隐私与运维影响

- 状态事件和内部原因可能敏感，使用不同 DTO；
- 状态变更要求项目权限、乐观锁和审计；
- 通知只携带最小公开说明；
- 批量迁移逐项授权和幂等。

## 迁移、兼容与回滚

首期无历史数据。新增状态应先让客户端支持未知值，再发布服务端。删除/合并状态需映射历史且保持原事件可解释。若用户选择简化 UI，可隐藏中间状态但底层仍保留统一事件。

## 复审触发器

- 真实项目普遍无法映射固定状态；
- 外部系统双向同步成为核心需求；
- 运营数据显示某状态长期无独立意义；
- 需要独立“等待用户/阻塞”语义且标签无法满足。
