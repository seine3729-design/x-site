# 0002 · Web 优先模块化单体

状态：已采纳  
日期：2026-10-23  
决策人：用户（2026-10-23 确认技术栈，形态随之采纳）  
适用范围：应用边界、部署、数据一致性、开发任务  
关联任务：D0-3、X0-1  
取代/被取代：具体语言与版本由 `adr/0006` 细化

## 背景与问题

项目目录为空，尚无技术栈。首期功能横跨身份、项目、内容、反馈、互动、治理和通知，但规模未知。需要选择既能快速交付完整纵切，又能保持权限、事务和未来扩展边界的架构。

## 约束与决策驱动因素

- Web 公开页面需要服务端渲染/元数据；
- 反馈状态、历史、贡献和审计需要单事务一致；
- 团队与部署规模尚未确认；
- 附件、通知和搜索索引需要异步处理；
- 不应因参考站技术或现有 x-site 技术机械选型。

## 决策

采用 Web 优先的模块化单体：

- 一个用户 Web，包含公开与成员页面；
- 一个运营后台，可与用户 Web 共工程不同路由组，是否独立构建在技术栈 ADR细化；
- 一个模块化 API 服务，单一关系数据库作为业务权威源；
- API 与 Worker 可分进程部署，复用领域和应用代码；
- 使用事务 Outbox 驱动附件、通知、搜索与外部同步；
- 首期不做原生 APP、微服务、独立消息总线和独立搜索集群；
- OpenAPI 是前后端机器契约。

本 ADR 只决定形态。具体语言、框架和版本基线由 `adr/0006` 确定：前端 Next.js 16.4 + React 19.3 + Bun 1.4，后端 Go 1.27.3 + Gin + PostgreSQL 18 + River，用户端与运营后台使用同一 Next.js 工程的两个路由组。

## 备选方案与放弃原因

### 微服务

可独立扩展，但引入分布式事务、消息兼容、部署、调试和权限传播成本，领域与规模尚不稳定。

### 全栈 Web 单进程且无 Worker

最简单，但附件扫描、通知和批量上线会阻塞请求，失败恢复差。仍需可独立运行的 Worker。

### 纯 SPA + API

后台可用，但公开项目/动态/反馈的 SEO、首屏和无 JavaScript 可读性较差。

### BaaS 直连表

原型快，但项目作用域授权、状态机、审计、附件隔离和复杂迁移容易散落在客户端/策略中。

## 正面后果

- 单库事务简化核心正确性；
- 一个团队能快速完成纵切；
- 模块边界为后续拆分保留接口；
- 部署和本地环境相对简单；
- 后台不需要直接访问数据库。

## 负面后果与风险

- 模块边界需要代码评审维护，否则会退化成大泥球；
- 某一模块故障可能影响同一 API 进程；
- 前后台同工程时要防止权限代码和 bundle 意外共享；
- Worker 与 API 的事件版本需要兼容回滚。

## 安全、隐私与运维影响

- Web/API/Worker 使用不同最小权限凭据；
- 后台入口、CSP、认证和部署可独立加固；
- 关系数据库是关键单点，需要备份、恢复和连接治理；
- Outbox/死信/队列延迟必须监控。

## 迁移、兼容与回滚

首期无迁移。若后续拆服务，以模块端口和 outbox 事件为边界，先复制读模型，再迁移写所有权；不共享跨服务表写入。若后台需要独立应用，可保留 API 和生成类型，仅移动前端路由。

## 复审触发器

- 某模块负载或发布节奏长期独立，且单体造成可测量影响；
- 团队规模和所有权要求独立部署；
- 数据驻留/合规要求模块分区；
- 搜索量或任务吞吐超过主库/Outbox 可控范围。
