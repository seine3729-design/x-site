# 0009 · 开放提交接口用 API Key + 来源白名单，不用签名

状态：已采纳  
日期：2026-10-23  
决策人：用户（2026-10-23：「还需要提供一个接口让其他网页可以提交反馈，并且运营后台记录这些反馈信息」）  
适用范围：`POST /open-api/feedback` 的鉴权、跨域、配额与落库可见性  
取代/被取代：不取代任何 ADR；与 `docs/07` 第 3 节的开放平台鉴权方案并存

## 背景与问题

需求是让**其他网页**能提交反馈。调用方是站外页面里的前端 JS，不是我们控制的服务端。

主平台的 `/open-api/*` 已经约定了一套鉴权（`docs/07` 第 3 节）：`Authorization: ApiKey <key_id>` 加 `X-Timestamp` / `X-Nonce` / `X-Signature`，按密钥做 HMAC 签名。那套方案是为服务端对服务端的内容推送设计的，前提是调用方能安全保管密钥。

浏览器里没有这个前提：任何放进页面 JS 的密钥都是公开的，签名也就只是把公开密钥换个形式写出来，拦不住任何人。强行要求签名只会让接入方把密钥放到自己服务端再转发一次——那对「在页面上加个反馈入口」这件事来说成本太高，大多数接入方会直接放弃。

## 决策

`POST /open-api/feedback` 用一套更轻、也更诚实的方案：

| 维度 | 做法 |
| --- | --- |
| 身份 | `X-Api-Key` 请求头携带密钥明文（`fbk_` 前缀 + 24 字节随机数的 base64url）；库里只存 SHA-256 哈希与末 6 位提示 |
| 来源 | 密钥上可配 `allowed_origins` 白名单（`scheme://host[:port]`）；**配了白名单时，不带 `Origin` 的请求一律拒绝** |
| 跨域 | 回显请求的 `Origin`，不输出 `Access-Control-Allow-Credentials` |
| 配额 | 按密钥每分钟 60 条 + 每日 `daily_limit` 条；另有按来源 IP 每分钟 120 条 |
| 写入范围 | 只能写一条反馈；项目由密钥决定，提交方不能指定；可见性取密钥的 `default_visibility`（默认 `members`） |
| 读取范围 | 没有。这个命名空间下不提供任何读接口 |
| 回源鉴权 | 豁免（登记在 `http.NewRouter` 的 `EdgeAuth.Exempt` 里）：第三方拿不到 `X-Edge-Secret` 或 `X-Service-Token` |
| 报文加密 | 不走。第三方不可能持有前台的 HPKE 客户端 |

把密钥当作「配额句柄」而不是「身份凭证」：它决定反馈落到哪个项目、按什么额度收，不授予任何读取权限。

关键取舍是**不带 `Origin` 时的行为**。浏览器跨域请求一定带 `Origin`，服务端直连不带。如果配了白名单却对无 `Origin` 的请求放行，那白名单可以靠去掉这个头绕过，等于没配。所以配了白名单就按「只接受浏览器提交」处理；需要服务端直连的接入方把白名单留空，靠密钥本身与配额控制。

不输出 `Access-Control-Allow-Credentials` 同样是必要的：接口不读 Cookie，浏览器也就不会带上任何会话，于是回显任意 `Origin` 只是让第三方页面能读到自己的提交回执，不构成代用户发起请求的通道（没有 CSRF 面）。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 沿用 `docs/07` 第 3 节的 HMAC 签名 | 浏览器里藏不住密钥，签名提供的是虚假的安全感，却把接入成本推高到「必须有自己的服务端」 |
| 放在 `/api/v1/feedback/intake` | 会落进 `/api/v1` 的报文加密分组，站外页面无法调用 |
| 只允许服务端直连（不支持浏览器） | 直接否掉「在页面上加个反馈入口」这个需求本身 |
| 用验证码代替配额 | 需要引入第三方验证码服务与前端 SDK，接入成本高；首期用配额 + 后台分诊已够 |
| 落库即公开（`default_visibility: public`） | 站外内容未经分诊直接公开，等于把垃圾内容发到前台 |
| 不限来源，只靠配额 | 密钥泄露后无法把损失收敛到特定站点；白名单让泄露的后果可控 |

## 正面后果

- 接入方在页面里加一段 `fetch` 就能提交，不需要自己的服务端；
- 密钥泄露的后果有界：只能往指定项目灌反馈，灌不出数据，且受配额与白名单约束；
- 外部反馈默认只对成员可见，先进后台分诊再决定是否公开；
- 后台能按 `source` 筛选、按 `api_key_id` 追溯到具体接入方。

## 负面后果与风险

- `/open-api` 下出现了两套鉴权：`/open-api/feedback` 用 Key，S4-6 的内容推送仍用签名。必须在 `docs/07` 第 3 节写明区别，否则后来者会按签名方案实现；
- 该路径免回源鉴权，直接暴露在源站上，受 CDN 保护更少；靠按 IP 限流与按密钥配额兜底；
- 密钥明文在接入方页面里可见，等同于公开配额；滥用时只能作废重建，接入方需要改页面；
- 按 IP 限流用 `c.ClientIP()`，在只信任已配置代理的前提下有效；代理配置错误会让限流失效。

## 安全、隐私与运维影响

- 密钥只存哈希，明文仅在创建响应里出现一次，审计与日志都不记明文；
- `page_url` 入库前丢弃查询串与片段（常带令牌、邮箱、订单号），见 `09` 第 10.1 节的数据最小化；
- `contact` 由提交者自愿填写，只在 `/api/admin` 响应里出现，不下发前台；
- 配额计数依赖 Valkey：计数器故障时**放行**而不是拒收——丢反馈比短时超额更糟；
- 密钥不可用（不存在、停用、已作废）统一返回同一个 `SIGNATURE_INVALID`，不让调用方据此探测密钥是否存在。

## 迁移、兼容与回滚

新增能力，不影响既有接口。回滚 = 从 `router.go` 摘掉 `/open-api` 分组注册并从 `EdgeAuth.Exempt` 移除该路径；已收下的反馈保留（`fb_feedback.source = 'open_api'`，`api_key_id` 可能指向已作废的密钥）。

## 复审触发器

- 出现规模化滥用，配额与白名单压不住；
- 需要给接入方提供读接口（查自己提交的反馈状态）——那时要重新考虑签名或 OAuth；
- S4-6 开放平台落地后，两套鉴权的共存方式需要再确认。
