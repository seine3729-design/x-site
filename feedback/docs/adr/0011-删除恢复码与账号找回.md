# 0011 · 删除恢复码与账号找回
状态：已采纳  
日期：2026-10-25  
决策人：用户（2026-10-25：「不需要生成恢复码 我知道恢复码是唯一的找回方式，丢了就找不回账号 这个也要删除」「删除忘记密码的逻辑啊。现在不需要忘记密码」）  
适用范围：社区账号（`fb_user`）的注册、改密、找回；相关接口、表结构与前台表单  
取代/被取代：取代 [`0007`](./0007-用户名账号与恢复码.md) 中关于恢复码与账号找回的部分（该 ADR 的其余结论仍有效）

## 背景与问题

`0007` 确立了「用户名 + 邀请码注册、不收集邮箱与手机号」。因为没有外部联系方式，
它把**一次性恢复码**作为唯一的自助找回途径：注册时发一串码、只显示一次、
用它加用户名可以重置密码。

用户要求把这套机制整个去掉，并且在被明确告知代价后确认：
**忘记密码就永久失去账号**。

这个要求之前提过一次，当时我给了三个方案（照做 / 删码但后台可重置 / 保留码但改成设置页自助生成）
并推荐第二个。用户这次的回答把选择说清楚了：照做，不要替代方案。

**另外值得记一笔：主平台早就做过同样的决定。** 根目录 `docs/adr/0001-不提供找回密码.md`
的标题就是「不提供找回密码（移除恢复码）」，结论是「没有恢复码、没有邮件/短信、
后台也不能重设用户密码」，放弃恢复码的理由写的是「用户普遍不保存，实际仍要走人工，
还要维护生成、展示、重新生成、作废整套流程」。

也就是说在这次改动之前，**社区模块才是与平台决策不一致的那一个** ——
`0007` 当初引入恢复码时没有对齐 `docs/adr/0001`。这次改完两边才一致。
这不改变决策本身（用户的要求是独立成立的），但它说明这个方向在本仓库里有先例，
而且那份 ADR 给出的放弃理由同样适用于社区。

## 决策

删除恢复码与「忘记密码」的全部实现。社区账号从此**没有任何找回途径**。

| 层 | 改动 |
| --- | --- |
| 领域 | 删 `IdentityService.Recover`、`newRecoveryCode`、`normalizeRecoveryCode`；`User` 去掉 `RecoveryHash`；`AuthResult` 去掉 `RecoveryCode`；`RegisterInput` 去掉 `AckNoRecovery`；`Repo.UpdateSecret` 去掉 recoveryHash 参数 |
| HTTP | 删路由 `POST /api/v1/feedback/auth/recover` 与对应 handler、`recoverReq`；`registerReq` 去掉 `ack_no_recovery` |
| 契约 | 0.41.0：删路径与 `FbRecoverRequest`；`FbRegisterRequest.required` 变为 `[handle, password, invite_code]`；`FbAuthResult` 去掉 `recovery_code` |
| 数据库 | 迁移 `00031`：解除 `fb_user.recovery_code_hash` 的 CHECK、加 `DEFAULT ''`、把已有值清空 |
| 前台 | 删 `/recover` 路由与 `RecoveryCodePanel`；注册表单去掉知情确认勾选框；登录页去掉「忘记密码」入口；改密不再展示新恢复码 |

唯一的改密路径是 `POST /api/v1/feedback/me/password`，**必须提供正确的当前密码**。
运营后台也没有代为重置的接口。

### 三个刻意的选择

**保留了注册页的告知文字。** 用户要删的是那个必须勾选的确认框，不是「密码丢了找不回」
这个事实。改成一条静态 `Alert`：不额外拦一道手，但注册前一定看得到。
后果不可逆的事情藏起来不是省事，是坑人。

**数据库只解除约束，不 DROP COLUMN。** DROP 在生产不可逆，而列里存的是哈希、
删了也换不回明文，收益为零；保留列让整个改动可以回滚，也让 sqlc 生成的字段类型
保持 `string`，不用连带改所有 `fb_user` 的扫描代码。Up 里把已有哈希清成空串 ——
留着一份无人校验却仍可被读取的敏感数据没有意义。

**没有把找回能力挪到运营后台。** 那是上一轮我推荐的 B 方案，用户这次没有选它。
加「管理员代为重置」会引入一条新的账号接管路径（需要权限点、审计、
以及「如何确认申请人就是账号主人」的流程），而这个社区连邮箱都不收，
根本没有能用来核验身份的东西 —— 那条路径只会变成社工攻击的入口。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 保留恢复码，改成设置页自助生成 | 功能没真正去掉，与要求不符 |
| 删恢复码，后台加「管理员重置密码」 | 用户未选。且无任何身份核验手段，这条路径的风险高于它解决的问题（见上） |
| 保留知情确认勾选框 | 用户明确说这条文案「也要删除」。改为静态告知，兼顾要求与告知义务 |
| `ALTER TABLE ... DROP COLUMN recovery_code_hash` | 生产不可逆；哈希删了也无法恢复原值，收益为零。留列可回滚，且不触发 sqlc 类型变化 |
| 改列为 nullable | sqlc 会把字段类型变成 `pgtype.Text`，连带改动所有 `fb_user` 扫描代码。保持 NOT NULL + DEFAULT '' 改动面最小 |

## 后果

**好的：**

- 注册流程少一个字段、少一屏（原来注册后要停下来让用户抄码）；
- 库里不再存在「可用于接管账号的凭据」，这类数据一旦泄露后果比密码哈希更直接；
- 账号安全模型变得极简：只有密码一条路，没有任何旁路可审。

**要承担的（已获用户确认）：**

- **用户忘记密码即永久失去账号**，连带丢失全部反馈历史与贡献值。运营无法帮忙。
- 这类用户只能用新邀请码重新注册，内测编号会变，旧账号成为僵尸数据。
- 如果将来改变主意要加回找回功能，**存量账号救不回来**：恢复码哈希已在迁移里清空。
  届时只能对新注册账号生效。

**留下的技术债：**

- `fb_user.recovery_code_hash` 列还在（恒为空串，有 `COMMENT` 标注已废弃）。
  确认这个决定稳定、不需要回滚之后，可以单独发一个迁移删掉它。

## 验证

- `./dev.sh go test ./internal/domain/feedback/`：通过。新增
  `TestNoPasswordResetWithoutOldPassword` 守住「改密必须提供正确的当前密码、没有旁路」，
  以及 `TestRegister/响应里不含任何找回凭据`（序列化后断言不含 `recovery` 字样）；
- 端到端（迁移 00031 已应用）：
  - `POST /api/v1/feedback/auth/recover` → **404**；
  - 注册请求体不带 `ack_no_recovery` → **200**，响应 `data` 只有 `expires_in / token / user`，
    整个响应无 `recovery` 字样；
  - 新账号入库后 `recovery_code_hash` 为空串；
  - 登录响应同样不含任何找回凭据；
- 前台：`/recover` → 404；注册表单字段顺序 `handle → password → nickname → invite_code`；
  页面无 `ack_no_recovery` 勾选框、无「忘记密码」链接。

## 复审触发器

- 用户反馈「忘记密码的人太多」；
- 开始收集邮箱或手机号（那时才有可核验的身份，找回方案需要重新设计）；
- 决定删除 `recovery_code_hash` 列。
