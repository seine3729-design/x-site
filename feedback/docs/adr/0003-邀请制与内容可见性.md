# 0003 · 邀请制与内容可见性

状态：已采纳（可见性矩阵待用户确认细节）  
日期：2026-10-23  
决策人：用户（2026-10-23 明确选择「注册必须邀请码」）  
适用范围：注册、项目加入、SEO、权限、缓存、通知  
关联任务：D0-2、B1-3、W1-1  
取代/被取代：无

## 背景与问题

参考站公开表达为封闭内测/邀请制，但也公开展示部分项目动态。用户尚未明确本项目是否完全邀请制，以及匿名访客能看到哪些内容。需要在增长、搜索可发现性与封闭测试隐私之间取得平衡。

## 约束与决策驱动因素

- 用户应能在注册前理解平台价值；
- 封闭项目的内容不能因首页、搜索、缓存或分享泄露；
- 邀请制会增加客服与账号恢复成本；
- 同一平台可能同时存在公开与封闭项目；
- 登录墙不应阻止公开内容 SEO。

## 决策

采用“平台可访问、注册需邀请、项目按模式加入、内容逐项可见”的组合：

- 平台首页、公开项目简介、公开动态和公开反馈允许匿名读取；
- **注册必须持有效邀请码**，不提供自助注册；邀请由平台管理员或获授权的项目所有者发放；
- 完整可见性矩阵见 `00` 第 8.2 节，是实现与测试的权威依据；
- 每个项目有 `open / application / invite_only / closed` 加入模式；
- 内容可见性为 `public / members / private`；
- 互动（提交、评论、投票、关注、回答议题）必须登录并满足项目资格；
- 私密反馈只对作者和明确授权的项目团队可见；
- 邀请 token 只存哈希、有限期/次数/角色，核销后仍显示用户将加入哪个项目；
- 公开范围收紧后立即清缓存与搜索索引。

## 备选方案与放弃原因

### 全站登录墙

最容易控制，但用户注册前无法理解价值，公开项目也失去分享与 SEO。

### 完全公开注册和项目

增长简单，但不适合封闭内测、未发布信息和安全反馈。

### 只有项目可见性，没有内容级可见性

模型简单，但同一项目无法同时发布公开公告与私密 Bug，用户容易误发敏感信息。

## 正面后果

- 公开价值与封闭测试可以共存；
- 项目方按自身阶段控制加入；
- 私密反馈有明确安全路径；
- 分享和搜索行为可预测。

## 负面后果与风险

- 可见性组合增加测试矩阵；
- 用户可能不理解项目成员内容和私密内容的差别；
- 可见性收紧需要跨缓存、搜索和通知及时传播；
- 平台邀请码与项目邀请可能造成概念混淆。

## 安全、隐私与运维影响

- 所有列表、计数、搜索、附件、通知和导出按可见性授权；
- 私密响应 `no-store`，HTML 元数据不泄露；
- 邀请/登录端点防枚举与限流；
- UI 在提交前解释谁能看到内容，并提示安全问题设为私密。

## 迁移、兼容与回滚

可通过配置把平台注册改为开放/邀请，不改变项目与内容模型。若用户决定全站封闭，只需把匿名路由改为登录要求并清公开缓存；若完全公开，仍保留私密级别用于安全/账号问题。

## 复审触发器

- 用户明确全站只服务单一私有团队；
- 公开内容带来不可接受的泄露/审核成本；
- 注册转化或邀请支持成本持续异常；
- 目标地区法规要求改变公开策略。
