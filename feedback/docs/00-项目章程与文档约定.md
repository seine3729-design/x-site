## 1. 项目定义

**工作名**：Feedback 社区。  
**一句话定位**：让产品团队发布内测动态，让真实用户提交可追踪的反馈，并通过公开处理过程形成持续协作的产品社区。

参考站公开页面体现的核心不是“发帖越多越好”，而是：

1. 项目方说明正在测试什么；
2. 用户按明确上下文提交问题或建议；
3. 运营分诊、回复并持续更新状态；
4. 上线结果回到社区，通知并认可贡献者。

本项目借鉴这条闭环，但不复制参考站品牌、原始文案、素材、邀请码或不可见的内部实现。

## 2. 要解决的问题

| 角色 | 当前问题 | 产品提供的结果 |
| --- | --- | --- |
| 内测用户 | 不知道应该测什么、反馈是否有人看、何时修复 | 清晰的测试任务、结构化提交、可追踪状态与通知 |
| 普通成员 | 重复反馈多，找不到已有讨论 | 搜索、筛选、相似项提示、投票与关注 |
| 产品/运营 | 反馈散落在聊天、表格和私信，无法统一分诊 | 项目级队列、负责人、优先级、标签和状态历史 |
| 研发 | 缺少设备、版本、复现步骤等关键上下文 | 按反馈类型动态采集必要信息，支持内部备注与关联版本 |
| 管理员 | 垃圾内容、泄露隐私与权限误配难追责 | 举报审核、最小权限、审计日志与可回滚操作 |

## 3. 目标与成功定义

### 3.1 MVP 目标

- 一个新用户可在 3 分钟内完成注册/受邀加入、找到项目并提交第一条有效反馈。
- 一条反馈有唯一编号、明确可见性、状态历史、项目方回复与关注通知。
- 运营可在一个队列内完成分诊、去重、分派、状态流转、关联版本与发布结果。
- 首页能同时承载项目动态、置顶公告、近期反馈和当前议题，但不演变为无边界的信息流。
- 所有高风险管理操作有权限校验和审计记录。

### 3.2 初始衡量指标

以下为 `[提议]` 的首月目标，正式上线前按实际规模调整：

| 指标 | 定义 | 初始目标 |
| --- | --- | --- |
| 首次反馈完成率 | 开始填写后成功提交的用户占比 | ≥ 65% |
| 有效反馈率 | 未被判定垃圾、空泛或无法理解的反馈占比 | ≥ 70% |
| 首次响应时长 | 提交至首次官方回复的时长 | P75 ≤ 24 小时 |
| 首次分诊时长 | 提交至进入明确处理状态的时长 | P75 ≤ 48 小时 |
| 状态透明度 | 已确认反馈中 14 天内有状态更新的占比 | ≥ 90% |
| 重复拦截率 | 提交前通过相似项提示避免的重复数 / 潜在重复数 | 只观测，首期不设硬目标 |
| 负向指标 | 举报成立率、误封率、通知退订率、删除请求处理超时数 | 必须持续观测 |

指标只用于改进产品，不用于强迫运营“刷状态”或诱导用户刷反馈。

## 4. MVP 范围

### 4.1 范围内

- 公开首页、项目目录、项目主页和项目动态；
- 登录、注册/邀请加入、个人资料和会话管理；
- 反馈提交、图片附件、列表、详情、搜索、筛选与状态时间线；
- 评论、官方回复、投票、关注与站内通知；
- 周期议题/结构化投票；
- 贡献值、贡献等级和被采纳记录；
- 运营后台：项目、成员、反馈分诊、内容、议题、邀请、举报、用户和审计；
- 基础反垃圾、内容安全、隐私删除和数据导出能力；
- 响应式 Web、可访问性与基础 SEO。

### 4.2 明确范围外

- 原生 iOS/Android APP；
- 私信、群聊、音视频直播和实时在线状态；
- 用户间关注关系、算法推荐和无限下拉成瘾机制；
- 充值、提现、商城、广告交易或任何具有现金价值的奖励；
- 完整项目管理工具，不替代 Jira/GitHub Issues；
- 与 GitHub、GitLab、Jira、飞书、Slack、Telegram 等外部系统的集成与双向同步；
- 邮件通道（账号不收集邮箱）、短信与第三方 IM 推送；
- 多语言、语言切换与 RTL 排版（首发只有简体中文）；
- 用户自助创建项目（只有平台管理员能创建）；
- 开放自助注册（必须邀请码）；
- 未经人工确认自动改变反馈优先级或自动承诺发布时间；
- 任意 HTML、可执行附件、大文件和视频上传；
- 多区域双活、微服务拆分和独立搜索集群（规模触发后再评估）。

## 5. 参与角色

| 角色 | 核心职责 | 边界 |
| --- | --- | --- |
| 访客 | 浏览公开项目、动态和公开反馈 | 不能提交、评论、投票或查看成员内容；**不能自助注册**，必须有邀请码 |
| 成员 | 提交反馈、评论、投票、关注、参与议题 | 只能编辑自己的未进入处理流程的内容 |
| 项目运营 | 发布项目动态、分诊反馈、管理议题和项目成员 | 仅限所属项目，不可处理平台级用户与配置 |
| 项目维护者 | 分派、更新研发状态、关联版本、写内部备注 | 内部备注不能被成员或访客读取 |
| 版主 | 处理举报、隐藏内容、临时限制用户 | 不能读取私密反馈正文，除非被项目授权 |
| 平台管理员 | **创建项目**、管理平台、角色、全局策略与申诉 | 高敏操作需重新认证并审计；不能重置用户密码（`adr/0007`） |

权限矩阵以 `07` 为页面说明、以服务端授权策略为执行权威。

## 6. 产品原则

1. **反馈闭环优先于互动数量**：状态透明和官方回应比点赞总数更重要。
2. **上下文一次采够但不过度采集**：按反馈类型渐进展示设备、版本、复现步骤等字段。
3. **公开有边界**：默认公开不等于全部公开，私密反馈、内部备注和个人数据严格隔离。
4. **不给虚假承诺**：`planned` 不代表固定发布日期，界面必须说明。
5. **用户拥有退出权**：可取消关注、关闭通知、导出数据、注销账号和申请删除内容。
6. **治理可解释**：隐藏、合并、拒绝、封禁都有原因、操作者与申诉路径。
7. **可访问、移动优先**：核心流程不用悬停、拖拽或颜色单独表达。
8. **先模块化单体，按证据扩展**：不为想象中的规模预先拆微服务。

## 7. 术语表

| 术语 | 定义 |
| --- | --- |
| 项目 `project` | 一个被测试或共创的产品空间，拥有成员、动态、反馈和议题 |
| 项目动态 `post` | 公告、测试任务、上线小结或讨论内容 |
| 反馈 `feedback` | 用户针对一个项目提交的 Bug、建议、内容需求或体验问题 |
| 分诊 `triage` | 确认类型、优先级、重复关系、负责人和下一状态的过程 |
| 官方回复 | 由项目运营或维护者发布、带身份标记的公开评论 |
| 内部备注 | 仅项目运营/维护者可见，不向提交者公开的协作记录 |
| 议题 `topic` | 有起止时间的社区问题，可为自由回答、单选或多选 |
| 关注 `subscription` | 订阅反馈或项目的状态与回复变化 |
| 贡献事件 | 可审计的贡献值增减记录，如反馈被采纳或因误判撤销 |
| 发布版本 `release` | 对外可见的版本/批次，用于关联已上线反馈与更新说明 |

决策 4 的连带结论：**没有邮箱就没有邮件通道**。因此通知只做站内；管理员不能直接重置用户密码。

**也没有任何密码找回途径**（`adr/0011`，2026-10-25）：不发恢复码、不发邮件短信，
唯一的改密入口要求提供当前密码。忘记密码即永久失去账号，这是已确认代价的产品决定。
（`adr/0007` 原本的一次性恢复码方案已被取代；这与主平台根 `docs/adr/0001` 的结论一致。）

### 8.3 P1：进入对应功能前确认

- 反馈类型和状态是否允许项目级自定义（当前：不允许）；
- 私密反馈是否允许版主查看（当前：不允许，需项目显式授权）；
- 评论是否支持一层回复（当前：支持一层）；
- 图片附件大小、数量与保留期（当前：≤ 10 MiB、6 张/条）；
- 贡献等级阈值与是否公开展示等级（当前：可隐藏，榜单登录可见）；
- 用户删除已被采纳反馈时公开署名如何处理；
- 是否允许成员发布自由讨论帖（当前：不允许，只有项目团队能发动态）。

### 8.4 已确定的范围约束

- **语言**：只有 `zh-CN`，界面文案仍集中在 locale 文件，便于以后扩展，但首发不做语言切换、不做 RTL、不做 hreflang。
- **通知**：只做站内通知。Web Push 列为 P2 可选，邮件通道不在规划内。
- **集成**：不提供 Webhook 出站和第三方 Issue 同步；`08` 中相关章节标记为范围外。
- **容量与部署区域**：仍需你确认，当前按 `10` 的初始假设估算，不影响 M0/M1 实现。

## 9. 风险登记

| 风险 | 可能影响 | 首期缓解 |
| --- | --- | --- |
| 参考站不可见功能被误当事实 | 返工、权限或数据模型错误 | 调研文件区分观察与推断，未知项显式待确认 |
| 功能过多导致 MVP 延迟 | 核心闭环迟迟不可用 | M1/M2 先交付项目动态与反馈闭环，奖励和集成后置 |
| 公开反馈泄露隐私或漏洞细节 | 用户与项目安全受损 | 私密可见性、提交提醒、自动检测、版主升级流程 |
| 投票和贡献值被刷 | 排序失真、社区信任下降 | 登录限制、速率限制、异常检测、可撤销账本 |
| 状态长期不更新 | 用户失去信任 | 运营 SLA、过期提醒、项目健康看板 |
| 管理权限跨项目泄露 | 严重数据越权 | 服务端项目作用域授权、自动化越权测试与审计 |

## 10. 决策与变更流程

- 跨模块、难回滚或涉及数据/安全的选择进入 `adr/`；状态只使用“提议、已采纳、已拒绝、已取代、已废弃”。
- 产品假设由用户明确确认后，回写本文件或 `01`，需要解释取舍时同时采纳 ADR。
- 复杂任务在实现前从 `specs/TEMPLATE.md` 建立规格，必须包含目标、范围内、范围外、依赖、验收和回滚。
- 发现文档之间冲突时停止实现，列出冲突位置并确认权威源，不静默选择方便实现的一份。
