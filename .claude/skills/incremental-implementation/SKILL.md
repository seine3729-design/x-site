# 增量实现

## 概述

一次只做一个可验证的切片：实现 → 测试 → 运行验证 → 下一片。每个切片结束时系统仍可构建、测试仍通过。

## 切片循环

```
实现最小完整片段 → 跑该端测试/构建 → 实际运行看结果 → 记录进度 → 下一片
```

单次写代码超过约 100 行还没运行过任何验证，就停下来先验证。

## 规则

1. **最简单可行**：先写直观正确的版本，性能优化等到有测量数据（见 `performance-budget`）。
2. **范围纪律**：只改任务需要的文件。看到其他问题，用下面格式汇报，不要顺手改：
   ```
   注意到但未处理：
   - admin/src/lib/format.ts 有未使用的导入（与本任务无关）
   ```
3. **始终可编译**：每片结束后该端构建通过；跨端改动时先让契约与后端可用，前端再接入。
4. **默认安全**：新开关默认关闭，新接口默认需要鉴权，新配置缺失时启动失败而不是静默使用危险默认值。
5. **可回滚**：迁移写 `Down`；破坏性改动拆成「新增 → 切换 → 删除旧的」三步。
6. **未完成的功能加开关**：通过 `site_config.features` 或构建期开关隐藏，不让半成品对用户可见。

## 各端验证命令（仓库根目录）

| 端 | 每片至少执行 |
| --- | --- |
| service | `./dev.sh go test ./...`；接口改动再 `curl` 一次真实请求 |
| apps | `./dev.sh run apps bun run check`；页面改动在浏览器打开确认 |
| admin | `./dev.sh run admin pnpm typecheck`；页面改动在浏览器打开确认 |
| mobile | `./dev.sh flutter analyze` + 相关 `flutter test`；界面改动在模拟器确认 |

同一份代码已经验证通过后，不要重复运行同一条命令；代码再改动后再跑。

## 常见借口

| 借口 | 事实 |
| --- | --- |
| 「最后统一测」 | 第一片的错误会让后面所有片都建立在错误之上。 |
| 「一起改更快」 | 出问题时没法知道是哪一处引起的。 |
| 「顺手重构一下」 | 重构和功能混在一起，评审和回滚都更难。 |

## 红线

- 多个无关改动混在一个切片里
- 构建或测试处于失败状态时继续写下一片
- 为只用一次的逻辑新建通用工具或抽象层
- 修改任务范围外的文件

## 验证

- [ ] 每个切片都执行过对应验证命令且通过
- [ ] 功能端到端可用（真实请求 / 浏览器 / 模拟器）
- [ ] 满足 `project-skills-index/references/definition-of-done.md`
