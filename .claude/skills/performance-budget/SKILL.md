# 性能预算

## 概述

预算与方案在 `docs/08`。原则：先测量、再优化；只优化测量证明的瓶颈。

## 关键预算（节选，完整见 `docs/08` 第 1 节）

| 指标 | 目标 |
| --- | --- |
| 首帧 | P50 ≤ 1.0s，P95 ≤ 2.5s |
| Web LCP / INP / CLS | ≤ 2.0s / ≤ 200ms / ≤ 0.05 |
| Web 首屏 JS | ≤ 90 KB（br） |
| 后台首屏 JS | ≤ 200 KB（br） |
| API 读 / 写 / 选源 P99 | ≤ 150ms / 300ms / 80ms |
| APP 冷启动 | ≤ 1.5s；刷剧 ≥ 58fps |

## 流程

1. **测量**：Go 用 `testing.B` 基准与 pprof；SQL 用 `EXPLAIN (ANALYZE, BUFFERS)`；Web 用 Lighthouse / Performance 面板；APP 用 DevTools 性能视图。
2. **定位**：找到最大的单项耗时，不要同时改多处。
3. **改动**：按下方清单选择最直接的手段。
4. **复测**：用同样的方法对比前后数据，写进提交说明或 PR。

## 常用手段

- 后端：游标分页替代 OFFSET；冗余列 + 复合索引；读穿缓存 + singleflight；计数先进 Valkey 再批量落库；批量写用 `COPY`。
- 选线/签名：目录前缀签名替代逐切片预签名；地区排序结果短缓存。
- Web：重模块动态导入；图片尺寸与懒加载；公共页面边缘缓存，个人数据二次请求。
- APP：控制器池 ≤ 3；按显示尺寸解码图片；重计算放 Isolate。

## 红线

- 没有测量数据就做「优化」
- 为了性能引入复杂缓存却没有失效策略
- 优化导致个人数据进入共享缓存
