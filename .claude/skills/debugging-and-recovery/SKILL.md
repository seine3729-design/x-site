# 调试与恢复

## 流程

1. **复现**：写出最短复现步骤（命令、请求、页面操作）。不能复现就先收集更多信息，不要改代码。
2. **收集证据**：
   - 容器状态与日志：`./dev.sh ps`、`./dev.sh logs <服务>`
   - 后端请求：用响应头 `x-request-id` 在日志中检索
   - 数据库：`./dev.sh psql` 查数据，`EXPLAIN ANALYZE` 查慢查询
   - 缓存：`./dev.sh valkey`
   - 前端：浏览器控制台与网络面板；APP：`flutter logs`
3. **缩小范围**：二分（注释掉一半、回退到上一个可用状态），每次只改变一个变量。
4. **写失败测试**：把复现步骤变成测试（见 `testing-and-verification`）。
5. **修根因**：修复导致问题的原因，而不是掩盖现象（例如不要用 `try/catch` 吞掉错误、不要加 `sleep` 等待竞态）。
6. **验证**：测试通过 + 原复现步骤不再出现问题 + 该端全部测试通过。

## 同一方法失败两次

停止微调，重新审视假设：列出已确认的事实与未确认的推测，换一种完全不同的定位方式（例如从日志转向最小复现程序），并向用户说明进展。

## 常见本地环境问题

| 现象 | 排查 |
| --- | --- |
| `./dev.sh up` 某容器不健康 | `./dev.sh logs <服务>`；端口冲突用 `./dev.sh doctor` |
| 前端依赖安装失败 | 依赖卷与锁文件不一致：`docker volume rm xsite_apps_node_modules`（或 admin）后重启 |
| apps 新增的路由目录不生效（404） | 容器内文件监听不一定能感知新目录：`./dev.sh restart apps` |
| service 不启动 | `service/go.mod` 是否存在；`./dev.sh logs service` 看编译错误 |
| 数据库结构不对 | `./dev.sh migrate status`；必要时 `./dev.sh reset`（会清空数据，先确认） |

## 红线

- 没有复现就修改代码
- 通过删除测试、放宽断言、吞掉错误让问题「消失」
- 未经确认执行清空数据的操作
