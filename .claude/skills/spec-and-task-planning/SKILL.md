# 需求澄清与任务拆解

## 概述

本项目的需求已经写在 `docs/`，任务编号在 `docs/11`。这个技能确保每次开发都从「对应文档 + 对应任务编号 + 明确验收标准」出发，而不是凭印象写。

## 何时使用

- 用户给的是一句话需求、截图或「做一下 XX 模块」
- 改动涉及两个及以上端（例如后台配置 + 后端接口 + 前台展示）
- 要开始 `docs/11` 中的某个任务

**不适用**：单文件、行为明确的小修复（直接用 `incremental-implementation`）。

## 流程

1. **定位**：找到对应任务编号（如 `S1-6d`）和文档章节（如 `docs/12` 第 4 节）。找不到任务编号时，说明这是新需求，先补到 `docs/11`。
2. **读依赖**：检查任务表「依赖」列，依赖未完成时告知用户，不要越过依赖去写。
3. **写迷你规格**（直接写在回复里，复杂时写到 `docs/specs/<任务编号>.md`）：

```
任务：S1-6d 选线算法与 /api/v1/lines
目标：按客户端 IP 返回排序后的线路列表
范围内：…
范围外：…（明确不做的事）
接口：GET /api/v1/lines?kind=video|image → { region, lines[…] }
数据：读 storage_line / storage_line_rule；健康分读 Valkey
验收：
  - 广东电信 IP 命中「电信优化」规则的线路排第一
  - 全部线路不健康时仍返回健康分最高的一条
  - 本地开发 X-Debug-Geo 头可模拟地区
假设：…
```

4. **拆切片**：每个切片能单独编译、测试、演示；优先「契约 → 后端 → 前端」或「最高风险的部分先做」。每个切片写清验收方式。
5. **请用户确认**规格与切片（用户已明确说「直接做」时可跳过确认，但仍要在回复中写出规格）。

## 切片示例

```
切片 1：迁移 + sqlc 查询（storage_line、storage_line_rule）→ 迁移 up/down 通过
切片 2：选线纯函数 + 单元测试（不依赖数据库）→ 表驱动测试覆盖排序规则
切片 3：handler + OpenAPI → curl 返回预期顺序
切片 4：Web 线路菜单接入 → 浏览器中可见并能切换
```

## 常见借口

| 借口 | 事实 |
| --- | --- |
| 「需求很清楚，不用写规格」 | 写出来才发现「范围外」和「验收」各人理解不同。 |
| 「先把整个功能写完再拆」 | 大块改动出错时无法定位，也无法分批评审。 |
| 「文档没写的我按常识补」 | 常识补的部分要列为假设并让用户确认。 |

## 红线

- 没有验收标准就开始写代码
- 任务依赖未完成却直接跳过
- 规格里没有「范围外」

## 验证

- [ ] 规格包含目标、范围内/外、接口、数据、验收、假设
- [ ] 每个切片都有可执行的验证方式
- [ ] 任务编号与 `docs/11` 对应（新任务已补录）
