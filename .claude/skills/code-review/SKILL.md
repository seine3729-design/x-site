# 代码评审

## 概述

从五个维度评审：正确性、可读性、架构一致性、安全、性能。每条意见标注严重级别，只提有依据的问题。

## 严重级别

| 级别 | 含义 | 是否阻止合并 |
| --- | --- | --- |
| 🔴 必须修改 | 错误行为、安全问题、数据风险、破坏契约 | 是 |
| 🟡 建议修改 | 可维护性、缺测试、边界情况 | 视情况 |
| 🟢 可选 | 风格、命名小建议 | 否 |

## 检查项

**正确性**
- 是否满足任务验收标准；错误路径、空数据、并发、超时是否处理
- 测试是否覆盖新行为，且断言有意义

**可读性**
- 命名表达意图；函数单一职责；没有死代码和调试输出

**架构一致性**（本项目重点）
- Go：handler/domain/store 分层未被破坏；SQL 在 `db/queries`
- apps：服务端代码在 `#lib/server`；没有 `{@html}`；BFF 不持有密钥
- admin：请求只走 `lib/http.ts`；服务端状态在 TanStack Query
- mobile：网络只走 `core/net`；令牌在安全存储
- 接口与 `service/api/openapi.yaml`、`docs/07` 一致

**安全**：按 `security-checklist` 抽查输入、鉴权、密钥、SSRF、日志。

**性能**：是否引入 N+1 查询、无界列表、首屏同步加载重模块、个人数据进入共享缓存。

## 输出格式

```
结论：可以合并 / 修改后合并 / 需要重做
🔴 service/internal/http/public/lines.go:42 未校验 kind 参数，非法值会走默认分支返回图片线路。建议用 binding oneof=video image。
🟡 缺少「全部线路不健康」场景的测试。
🟢 selectLines 可改名为 rankLines，更贴近行为。
```

## 红线

- 没有看完整改动就下结论
- 只给风格意见而忽略行为问题
- 意见没有文件位置和理由
